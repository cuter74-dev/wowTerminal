## #33 — Cross-window tab reattach (drag-merge) + drag a tab outside to create a new window

No main/secondary window concept: dragging any window onto another merges them, and dragging a tab outside the window opens a new window at that location.

### What / Why / How
- **Drag-merge** (WKWebView can't do cross-window DnD → detect via OS window movement):
  - Every window detects its own movement via `getCurrentWindow().onMoved` → broadcasts the title-bar point as a global event `wt://winpos`.
  - Each window shows a drop overlay (`MergeDropOverlay`) if that point is within its area.
  - When movement stops (300ms debounce = release), find the target window via `getAllWebviewWindows`, protect the session with `mark_session_detached` (backend detach_guard), then send `wt://merge`{targetLabel,...} → the target window adds a tab attaching that session, and the source window closes the tab/window. Symmetric, no main/detached distinction.
- **Drag a tab outside → new window**: during a tab pointer-drag, if the cursor leaves the window boundary (or goes below the tab bar) and is released, it detaches. Added position x,y to `open_detached_window` → create a new window at the release screen coordinates.
- **Bug fix**: detached (attach-mode) windows don't spawn and so didn't call `onSession`, leaving `sessionByLeaf` empty → on merge the session couldn't be found and a new shell was launched, losing the content. Fixed to call `onSession(attachSessionId)` even in attach mode (keeps session/scrollback across chained detach/merge).
- Backend: `mark_session_detached(sessionId, kind)` command (same detach_guard as open_detached_window). Added `core:window:allow-close`/`allow-set-focus`, `core:event:allow-emit`/`allow-listen` to capabilities.

### Limitations
- "Fully releasing outside" may not work depending on whether WKWebView delivers mouse events all the way outside the window (boundary/below-tab-bar fallback kept). Merge fits the intentional gesture (dragging onto another window) but can also trigger when simply overlapping windows.

## #34 — Korean IME double-consonant breakage + leftover prompt on SSH connect

### What / Why / How
- **Korean IME double consonants (있/았/껐/짰)**: diagnostic logs found the root cause — when typing `ㅆ` (=Shift+ㅅ), the incoming **Shift keydown** was classified as a "non-character, non-backspace key" by the IME handler and called `resetIme()`, clearing the composing character, the mirror state (imeSent), and the textarea. As a result `ㅆ` leaked as a standalone jamo (`이ㅆ`) and the mirror went out of sync with the actual content, so it couldn't be deleted either.
  - Fix: during composition, **pass standalone modifier keys (Shift/Control/Alt/Meta/CapsLock) through without reset** to keep the mirror session (the `imeActive` block in `customKeyEventHandler`).
- **Leftover prompt on SSH connect**: when injecting the OSC 7 cwd hook at runtime, readline echoed the command (~240 chars) verbatim with a line wrap → screen scroll. The previous absolute cursor save/restore (ESC7 saved on the frontend + ESC8 restored) was invalidated by the scroll, leaving a leftover prompt at the top (window-height dependent). `stty -echo` had no effect since it's the shell readline's own echo.
  - Fix: at injection time, **compute the number of echo-wrap lines N from the prompt width (`term.buffer.active.cursorX`) and command length** (a digit-convergence loop); at the end of setup `printf '\033[NA\r\033[J'` **moves up exactly N lines relatively to erase the echo**. Being relative, it's accurate even if scrolling occurs, and the banner is preserved.
- Removed all diagnostic console.log (IME keydown/mirror/onData, SSH raw bytes).

### Verification
- After rebuild, connecting a new SSH tab → single prompt, banner preserved, no leftover; 있/double-consonants/uppercase input and delete confirmed.

## #35 — Alt-screen wheel scroll

### What / Why / How
- Background: the user reported scrolling didn't work on the remote → diagnosis found the remote was running inside **tmux** (green status line). tmux uses the alternate screen so output doesn't accumulate in the emulator scrollback, so the wheel does nothing (tmux needs `set -g mouse on`). By the same principle, alt-screen apps like less/man/git log/vim have no default wheel scroll.
- Added: when in the **alt screen and the app isn't using mouse reporting**, convert wheel deltaY to up/down arrows (respecting app cursor key mode: `\x1bOA/B` vs `\x1b[A/B`) and send to the PTY → wheel scroll in less/man/vim, etc. Implemented with `term.attachCustomWheelEventHandler`, branching on `term.buffer.active.type`/`term.modes.mouseTrackingMode`.
  - The line count is converted via `deltaY / cell height (container.clientHeight/rows)` (natural for both trackpad pixels and wheel), min 1 line, max rows.
  - Apps with mouse mode on (tmux mouse on, etc.) and the normal screen are left as-is (return true) to keep existing behavior.
- Added a settings toggle `terminal.altScreenWheelScroll` (default on) — settings.ts type/default, SettingsModal 11-language label + checkbox.

## #36 — Copy selected terminal text (⌘C/Edit menu/tmux) — **Done**

> Copy behavior confirmed (user test complete). Committed after removing all diagnostic console.log.

### Symptom
- After drag-selecting text in the terminal, copy didn't work. Especially impossible **inside tmux**.

### Cause Analysis (stepwise)
1. xterm.js selection is its own model, not DOM selection (`document.getSelection`) → the macOS default copy (⌘C/Edit menu) copies empty content.
2. Confirmed **copy works outside tmux** → so the frontend fix below works and `navigator.clipboard` is fine.
3. The real cause of **failing only inside tmux**: because of tmux's `set -g mouse on` (turned on earlier for scrolling), the **drag goes to tmux** so no xterm-local selection is created (no selection, so ⌘C has nothing to copy). The `Shift+drag` workaround also doesn't work in this environment (the drag itself doesn't happen — presumably xterm's shift-bypass doesn't work).

### Work Done (src/components/Terminal.tsx)
- **⌘C key handler**: intercept `metaKey+c` (when there's a selection) in `customKeyEventHandler` and copy `term.getSelection()` via `navigator.clipboard.writeText`. Pass through when no selection (preserve Ctrl+C SIGINT).
- **copy event listener** (container scope): for the Edit menu / right-click Copy — `clipboardData.setData(text/plain, selection)` + `preventDefault`.
- **OSC 52 handler**: `registerOscHandler(52, …)` — on receiving `\e]52;c;<base64>`, base64-decode and write to the system clipboard. **Ignore read requests ("?")** (so the remote can't read the clipboard). When tmux (set-clipboard on)/vim etc. send this sequence on copy, it reflects to the system clipboard.
- Removed all diagnostic console.log after confirming behavior.

### tmux config (remote ~/.tmux.conf, applied by the user, tmux 3.4)
```
set -g set-clipboard on
set -ga terminal-overrides ',*:Ms=\E]52;%p1%s;%p2%s\007'
```
→ so tmux copy (drag/copy-mode) puts content into the system clipboard via OSC 52. (Awaiting confirmation of OSC 52 receive logs.)

### Result / Verification
- Outside tmux: drag-select → ⌘C copies normally.
- Inside tmux: after applying `set -g set-clipboard on` + `set -ga terminal-overrides ',*:Ms=\E]52;%p1%s;%p2%s\007'` (tmux 3.4), drag/copy-mode copy → reflected to the system clipboard via OSC 52. User test complete.

### Follow-up Notes
- xterm shift-bypass (local selection with Shift+drag in mouse mode) doesn't work in this environment → for tmux, the OSC 52 path is the standard. Review as a separate issue if needed.

## #37 — Mouse click coordinates printed after alt-screen + leftover top prompt on SSH

### What / Why / How
- **Leftover top prompt — remove OSC 7 runtime injection (root fix)**: confirmed via A/B that turning off injection and connecting makes the leftover disappear. The cursor cleanup that erased the injection-command echo (ESC7/8 → cursorX-based ESC[NA) remained vulnerable to per-server prompt width/wrapping/tmux alt-screen, repeatedly causing the leftover. Abandoned the approach entirely and **fully removed runtime injection**. The OSC 7 *receive* handler is kept → if the user adds one hook line to the remote `~/.bashrc`, cwd sync works cleanly (comment/guidance provided).
- **Mouse click coordinates printed**: when an alt-screen TUI (vim/tmux/Claude Code etc.) exits with mouse tracking mode on, clicks/drags at the normal shell prompt print coordinate text (`\e[<0;30;5M`). Use `term.buffer.onBufferChange` to **disable tracking/focus modes (?1000/1002/1003/1004/1005/1006/1015) on returning from alt to normal screen**. Safe since the normal shell doesn't use mouse mode.
