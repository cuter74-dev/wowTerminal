## #156 — Ghostty 1.4.0 리뷰 기반 터미널 보강: bracketed paste, OSC 8 링크, bash OSC 133

### 무엇을 / 왜

GeekNews에 올라온 Ghostty 1.4.0 릴리스 노트(https://news.hada.io/topic?id=36121)의 32개
항목을 우리 구조(xterm.js + Tauri + portable-pty)와 대조했다. 대부분은 Ghostty 자체 렌더러·
파서 얘기라 xterm.js 위에서는 해당이 없거나 이미 있었고, **붙여넣기 보호 / 링크 안전 / 셸
통합 종료 상태** 세 갈래에서 우리 코드에 실제 결함이 있었다.

| Ghostty 항목 | 우리 상태 | 조치 |
|---|---|---|
| 붙여넣기 보호 우회 수정 | 우클릭 메뉴 붙여넣기가 `term.paste`를 안 거침 → **버그** | 수정 |
| OSC 8 링크 → 임의 명령 실행 수정 | `linkHandler` 미지정 → xterm 기본(window.confirm+window.open)이 스킴 무검사 | 수정 |
| 셸 통합의 실제 종료 상태 전달 | bash + 기존 `PROMPT_COMMAND`면 C 마커가 프롬프트 시점에 나감 → **버그** | 수정 |
| ⌘↑/⌘↓ jump_to_prompt | 이미 있음(OSC 133 마커 점프) | — |
| 소수 배율 선명 렌더링 | 이미 소수 DPR에선 DOM 렌더러로 전환 | — |
| OSC 52 읽기 차단 | 이미 쓰기만 허용, 읽기(`?`) 무시 | — |
| 숨김 탭 GPU 자원 해제 | 탭마다 WebGL 컨텍스트 상주(display:none). 웹뷰의 컨텍스트 수 한도를 넘으면 오래된 탭이 컨텍스트를 잃고 DOM으로 영구 폴백 | **후속 후보**(실기기 검증 필요) |
| 한글 조합 중 방향키 확정 | IME 미러 경로가 복잡해 실기기 확인 필요 | 후속 확인 |
| 스크롤백 압축, pty/파싱 스레드 분리, Kitty 그래픽, OSC 5522, GTK 렌더러, esctest | xterm.js 내부 영역이거나 대형 작업 | 해당 없음 |

### 어떻게

1. **붙여넣기** (`Terminal.tsx` `doPaste`): `sendToSessionRef`(PTY 직접 쓰기) →
   `termRef.current.paste(txt)`. xterm의 paste 경로라 bracketed-paste 래핑과 `\n→\r` 정규화가
   적용된다. ⌘V/Ctrl+V는 원래 이 경로였고 컨텍스트 메뉴만 빠져 있었다.
2. **OSC 8** (`Terminal.tsx` XTerm `linkHandler`): `http:`/`https:`/`mailto:`만 opener로 열고
   (opener 기본 스코프와 동일) 나머지는 무시. `activate(event, text, range)`의 `text`는 표시
   텍스트가 아니라 **대상 URI**라서, 표시 텍스트는 `range`로 버퍼에서 읽어 비교한다. 스킴·끝
   슬래시를 뺀 값이 다르면(`[문서](https://evil…)` 류) 플러그인 dialog `confirm`으로 실제 주소를
   보여주고 확인받는다. 문구는 STR에 11개 언어로 추가(`linkMismatch`). 판정 함수는 node로
   javascript:/file:/data:/커스텀 스킴 차단, 대소문자 스킴 허용, 불일치 텍스트 판정 확인.
3. **bash OSC 133** (`pty/manager.rs`): 원인은 `__wt_precmd`가 preexec 가드(`__wt_pe`)를
   **PROMPT_COMMAND 도중에** 0으로 리셋한 것. 뒤이어 사용자 훅이 실행될 때 DEBUG trap이 C를
   보냈다(실행 시간에 프롬프트 대기 시간이 섞이고 장시간 명령 알림이 오발). 리셋을
   PROMPT_COMMAND 맨 끝의 `__wt_arm`으로 옮기고, 가드를 1로 시작해 첫 프롬프트 전 C도 없앴다.
   rc 본문을 `BASH_RC` 상수로 빼고, 실제 bash를 `PROMPT_COMMAND='true user_hook'`과 함께 띄워
   마커·프롬프트 순서를 검사하는 테스트 추가. **옛 rc로 돌리면 실패함을 확인**
   (`["C","D;0","C","P",…]` vs 기대 `["D;0","P","C",…]`).

검증: `cargo test --lib` 50개 통과, `npm run build`(tsc) 통과.

커밋: `5b08c78`(붙여넣기), `f8a331a`(OSC 8), `f15976a`(bash). CHANGELOG `[Unreleased]` Fixed 3건.
릴리스는 아직 안 함(묶어서 배포하는 규칙) — GitLab 한국어 미러도 릴리스 때 함께.

## #157 — 출력 파이프라인 성능: PTY 출력 합치기, 히스토리 O(1) 링버퍼

### 무엇을 / 왜

#156에서 "해당 없음"으로 넘겼던 Ghostty의 **스크롤백 압축 / 성능 개선**을 실측으로 다시 봤다.
Ghostty가 pty 읽기와 파싱을 분리한 이유(macOS 커널의 pty read ~1 KiB 제한)가 우리에게도 그대로
해당했다. 이 머신(macOS, 우리와 같은 8 KiB 버퍼)에서 10 MB 출력 시:

| 자식의 쓰기 단위 | read 횟수 | 평균 |
|---|---|---|
| 100 B 줄 | 75,822 | 133 B |
| 4 KiB | 9,998 | 1,010 B |
| 64 KiB | 9,925 | 1,020 B |

read 1회 = `pty:output` 이벤트 1개(히스토리 append + base64 + JSON + 웹뷰 IPC + JS 디코드 +
`term.write`). 게다가 `HistoryStore::append`는 512 KiB가 찬 뒤 `Vec::drain(..excess)`로 **1 KiB마다
~512 KiB memmove**를 했고, 그 mutex는 pty·ssh **전 세션 공유**다. 벤치(릴리스, 10 MB/1 KiB 청크):
**83.4 ms → VecDeque 0.49 ms(169배)**, 결과 바이트 동일.

### 어떻게

1. `HistoryStore`: `Vec<u8>` → `VecDeque<u8>`. cap보다 큰 단일 청크는 꼬리만 넣는다.
2. PTY reader를 **reader / forwarder 두 스레드**로 분리(bounded `sync_channel(256)`).
   `forward_output`은 청크 하나를 기다린 뒤 **이미 쌓인** 청크만 64 KiB까지 붙여 sink를 1회 호출한다.
   혼자 온 청크(타이핑 에코)는 즉시 나가므로 지연이 늘지 않고, 합치기는 sink가 밀릴 때만 일어난다.
   forwarder가 밀리면 reader가 막혀 종전과 같은 역압이 걸린다. `closed`는 마지막 데이터 뒤.
   데몬도 같은 `PtyManager`를 쓰므로 함께 적용된다.

테스트 3개 추가: `forward_output` 결정적 합치기(1 KiB×100 → `[65536, 36864]`), 히스토리 링,
실제 PTY + 느린 sink(2 ms) 통합. **합치기를 끄면 결정적 테스트가 실패**함을 확인. 실측 sink 호출
**405 → 48회**, 같은 출력 처리 시간 1.02 s → 0.13 s. `cargo test --lib` 53개 통과, clippy 경고 없음.

### 스크롤백 압축은 적용 안 함 (판단 근거)

스크롤백 버퍼는 xterm.js가 소유한다(BufferLine = 셀당 Uint32×3 = 12 B, 줄마다 열 수만큼 고정 할당).
Ghostty처럼 화면 밖 페이지를 압축하려면 xterm.js를 포크해야 한다. 기본값 1000줄에서는 터미널당
1.4~2.4 MB라 문제가 안 되지만, 설정 최대치 100,000줄이면 **터미널당 144~240 MB**다(탭 10개면
GB 단위). 큰 스크롤백 사용자를 위한 현실적 선택지는 설정 UI의 메모리 안내/상한 조정 정도 — 후속 후보.

남은 후보: SSH 출력 경로 합치기(russh 패킷이 이미 커서 효과 작음), 숨김 탭 WebGL 해제(#156 후속).

커밋: `7d31b8c`. CHANGELOG `[Unreleased]` Changed 2건.

## #158 — IME 회귀 테스트: 실기기 입력 이벤트 녹화 → 실제 Terminal에 재생

### 무엇을 / 왜

다른 터미널 조사(Wave·JetBrains·Orca 등)의 결론은 "xterm.js 유지, 그 위의 완성도를 올린다"였다.
그중 가장 효과가 큰 것이 입력 회귀 테스트다. 우리 입력 버그(#83/#88/#100/#133/#136/#140/#147)의
공통 원인은 **실제 WebView가 우리가 가정하지 않은 순서로 IME 이벤트를 보냈다**는 것이다. 기존
`inputSelfTest.ts`는 손으로 쓴 시퀀스라 상상한 순서만 검사할 수 있고, 돌리는 절차도 수동이다
(앱 종료 → sqlite 백업 → 플래그 주입 → 재실행 → 파일 확인).

Orca(stablyai/orca, MIT, Electron+xterm.js)는 같은 문제를 실기기에서 녹화한 DOM 이벤트 트레이스를
happy-dom의 실제 xterm에 재생하고 PTY 바이트를 단언하는 식으로 다룬다(IME 단위 테스트 ~45, e2e ~30).
그 방식을 가져왔다.

### 어떻게

1. **테스트 러너**: vitest 5 + happy-dom 21, `npm test`. `vitest.config.ts`가 vite define
   (`__APP_VERSION__` 등)을 같이 정의한다.
2. **리플레이 하니스** (`src/test/imeReplay.tsx`): **실제 `<Terminal>` 컴포넌트**를 렌더하고
   Tauri `invoke`/`listen`만 목(`tauriMock.ts`, `setup.ts`). 프로덕션 입력 코드를 모듈로 빼내는
   리팩터링 없이(그 자체가 위험) 그대로 테스트한다. 이벤트마다 녹화 당시 textarea 값/선택을
   **디스패치 전에** 적용하고, 녹화 간격을 가짜 타이머로 재생(80 ms 창·setTimeout(0) 지연 재현).
   `pty_write`로 간 바이트를 디코드해 돌려준다.
3. **트레이스 형식** (`src/imeTrace.ts`): UA(맥 미러 경로 선택), `cmpLatched`(A형/B형),
   이벤트 목록, 정확한 `expectedPty`, 사람이 읽는 `expectedLines`(DEL/CR 적용 후 셸이 실행할 줄).
4. **합성 픽스처** (`syntheticTraces.ts`): self-test T1–T7을 같은 순서·간격으로 이식. 7개 모두
   `expectedLines`가 self-test의 검증 기준과 일치함을 확인한 뒤 바이트 골든을 채웠다.
5. **변이 테스트로 검증**: 지난 수정 4개를 하나씩 되돌려 봤다 — #140(조합 커밋 스페이스)→T7,
   #97(미러 기준선)→T4, #100 래치→T5, #100 nbsp→T6가 **정확히 해당 테스트만** 실패.
6. **인앱 녹화기** (`src/imeTraceRecorder.ts`): 팔레트 "입력 트레이스 녹화 (새 탭)" → 새 로컬 탭에서만
   녹화(리플레이가 새 Terminal에서 시작하므로 IME 상태를 맞추기 위함), 탭에 노란 경고 줄(PTY로는
   안 보냄). "입력 트레이스 중지 및 저장" → 저장 다이얼로그. 윈도우 캡처 단계에서 이벤트를 보고
   (핸들러들이 보는 textarea 값 그대로), 그 터미널이 PTY로 보낸 문자열을 `expectedPty`로 함께 담는다.
   자동 전송 없음. 문구는 11개 언어.
7. **왕복 테스트**: 합성 트레이스 재생 중 녹화 → 녹화본의 expectedPty = 실제 전송분, 녹화본을 다시
   재생하면 같은 바이트(7개 전부).

### 걸린 것

- `JSON.stringify`는 DEL(0x7f)을 이스케이프하지 않아 "Backspace가 안 간다"로 오진할 뻔했다 —
  실패 메시지는 제어 문자를 `\x7f`로 보이게 출력한다.
- happy-dom은 `keyCode`/`data`/`isComposing` 이벤트 init을 무시해 getter로 강제한다.
- happy-dom에서 **일반 `Event`가 `instanceof CompositionEvent === true`** — 녹화기가 paste를
  composition으로 분류해 클립보드를 놓쳤다(왕복 테스트가 잡음). 이벤트 분류를 instanceof가 아니라
  `type`으로 바꿨다.

검증: `npm test` 16개 통과(+ 녹화 픽스처 없음 표시 1 skip), `npm run build`(tsc) 통과.
**실제 앱(WKWebView)에서 녹화기를 돌려 보지는 않았다** — 다음 단계에서 실기기 녹화와 함께 확인.
