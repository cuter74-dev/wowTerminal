## #137 — 전송 시 이름 충돌 확인 (덮어쓰기 / 새 이름 / 건너뛰기)

### What / Why
- 다운로드는 대상 폴더에 같은 이름이 있어도 **묻지 않고 덮어썼다** — 원본을 잃을 수 있다.
- 업로드는 단일 파일일 때만 브라우저 `confirm()`으로 물었는데, 다중 선택(#135)·폴더 전송은 무확인이었고, `confirm()`은 `prompt()`가 얼어붙던 #134와 같은 WKWebView 계열이라 애초에 신뢰할 수 없었다.
- **범위 결정**: 폴더 내부 파일까지 개별로 묻지는 않는다. 재귀 전송 도중 백엔드가 프론트에 되묻고 대기하는 프로토콜이 필요해 `sftp.rs` 전송 루프를 새로 설계해야 하는데, 얻는 것에 비해 과도하다. **최상위 전송 항목 단위**로만 확인하고, 폴더끼리 부딪히면 기존 동작인 병합을 그대로 쓴다.

### How — 백엔드 (`src-tauri/src/ssh/commands.rs`)
- `sftp_download` / `sftp_upload`에 `dest_name: Option<String>` 추가. 있으면 그 이름으로 저장/업로드하고, 없으면 종전대로 basename.
- `validate_dest_name()` 신설 — 빈 이름·`.`·`..`·경로 구분자(`/`, `\`)를 거부. 방금 커밋한 #136의 인라인 basename 방어를 이 함수로 흡수해, **사용자가 고른 새 이름에도 똑같이** 적용한다(사용자 입력이 그대로 경로에 조인되므로 원격이 준 이름과 같은 이탈 위험).
- 재귀 전송 자체는 손대지 않았다 — 업로드의 `create_dir(remote)`, 다운로드의 `create_dir_all(local)`이 전달받은 목적지 경로를 그대로 쓰므로 새 이름이 자연히 반영된다.

### How — 프론트 (`src/components/FileBrowser.tsx`)
- `ConflictModal` — 기존/새 항목의 크기·수정시각을 나란히 보여주고 **덮어쓰기(폴더끼리면 병합) / 새 이름으로 저장 / 건너뛰기 / 취소**. 남은 충돌이 있으면 "나머지 N개에도 동일 적용" 체크박스. Enter=새 이름 저장, Esc/배경=취소.
- `planTransfers(entries, dest, destLabel)` — 전송 **전에** 목적지 목록과 대조해 충돌을 순차 해소하고 `(항목, 목적지 이름)` 계획을 만든다. `askConflict`가 모달 선택을 Promise로 돌려줘 루프에서 `await`.
  - **`taken` 집합**: "이미 있는 이름 + 이번 전송에서 새로 차지한 이름". 자동 새 이름끼리 서로 겹치지 않게 한다.
  - **일괄 적용 시 rename**: 첫 항목이 고른 이름을 나머지에 재사용하면 안 되므로, 모달을 직접 띄운 항목만 사용자 입력을 쓰고 따라온 항목들은 각자 `uniqueName()`으로 새로 배정한다.
  - `const r: ConflictResolution = bulk ?? await askConflict(...)`의 **명시 주석은 필수** — 아래 `bulk = r`가 bulk의 흐름 타입을 r에 의존시켜, 없으면 순환 추론(TS7022)으로 컴파일이 깨진다.
- 적용 경로 5곳 전부: 툴바 ← / →, 컨텍스트 메뉴, 패널 간 드래그(양방향), OS 드래그 앤 드롭.
  - OS 드롭은 경로 문자열만 와서 폴더 여부·크기를 모른다 → 합성 항목으로 **이름 충돌만** 검사하고, 모달의 "새 항목" 칸은 `—`로 표시. 이름이 겹칠 수 있어 원본 경로는 `Map<FileEntry, string>`으로 되찾는다.
- 다운로드 목적지는 로컬 패널이 아닐 수 있어(폴더 선택 다이얼로그) `local_list_dir`로 그 폴더를 따로 읽어 대조한다. 목록을 못 읽으면 충돌 검사 없이 진행 — 실패는 전송 큐에 에러로 남는다.
- 정리: 옛 `confirm()` 호출, 죽은 i18n 키 `confirmOverwriteLocal`·`confirmOverwriteRemote`(11개 언어분), 더는 쓰이지 않는 `nameExists()` 제거(`noUnusedLocals`로 컴파일 에러가 된다).
- 충돌 모달 문자열은 컴포넌트 로컬 사전(`CONFLICT_STR`)으로 11개 언어 모두 작성.

### 이슈 번호 정리
- 이슈를 새로 만들었더니 **#136**이 발급됐는데, 워킹 트리에 이미 `(#136)`을 참조하는 미커밋 작업이 있었다.

## #138 — 파일 브라우저 열 머리글 정렬

### What / Why
- 정렬이 **디렉토리 우선 + 이름 오름차순 고정**이었다. 큰 파일을 찾거나 최근에 바뀐 파일을 보려면 눈으로 훑어야 했다.
- 이미 표시 중인 세 열(이름/크기/수정)이 있으니 머리글 클릭이 가장 자연스러운 UI.

### How
- `sortEntries(listing, sort)` — `SortState = { key: "name"|"size"|"modified", dir: "asc"|"desc" }`.
  - **디렉토리는 정렬 기준과 무관하게 항상 위에 묶는다** — 기존 동작이자 대부분의 파일 관리자 관행.
  - 크기·수정시각이 같으면 이름으로 갈라 **안정 정렬**을 만든다(같은 크기 파일들이 매번 다른 순서로 튀지 않도록). 이름 정렬일 때만 이 비교에 방향을 적용한다.
  - `modified`가 없는 항목은 0으로 취급.
- `nextSort()` — 같은 열 재클릭이면 방향 반전, 다른 열로 옮기면 그 열의 기본 방향. **이름은 오름차순, 크기·수정시각은 내림차순**으로 시작한다(큰 것/최근 것을 먼저 보는 게 보통이라 한 번 더 누르는 수고를 던다).
- **상태는 부모(`FileBrowser`)가 소유**한다. `sortEntries`는 화면 표시 말고도 **Shift-클릭 범위 선택(#135)**과 다운로드·업로드 대상 순서에 쓰여서, 넷이 같은 순서를 보지 않으면 화면에 보이는 것과 다른 파일이 선택된다. 네 호출부 모두 해당 패널의 정렬을 넘기도록 연결.
- 로컬·원격이 각자 상태를 가지며 `localStorage`(`wt.files.sort.local` / `.remote`)에 저장 — 값이 깨져 있으면 기본값으로 폴백.
- `Panel`에 `sortableTh()` 추가 — 활성 열은 밝은 색 + ▲/▼.
- 문자열 추가 없음: 열 이름은 이미 11개 언어로 번역돼 있고 화살표는 번역이 필요 없다.

## #139 — 인라인 자동완성 수락 키를 Shift + → 로

### What / Why
- "Tab이 자동완성 키 아니었나, 바꾸지 않았나?"라는 물음에서 이력을 조사해 보니 **두 번 뒤집혀 있었다**.

| 시점 | 수락 키 | 이유 |
|---|---|---|
| #102 | Tab → **→ / End** | Tab이 셸의 파일·디렉토리·명령 완성과 충돌 — 제안이 뜨면 셸 완성을 못 함 |
| #127 | →/End → **Tab** | →/End가 순수 커서 이동과 충돌, tmux/TUI에서 무동작 |

- 즉 #127은 **#102가 Tab을 버린 바로 그 이유를 되돌린** 셈이고, 셸 완성 충돌이 되살아나 있었다. 예: `cd Doc`까지 쳤을 때 히스토리에 `cd Documents/project`가 있으면 셸 완성을 기대하고 Tab을 눌러도 히스토리 제안이 들어온다.
- 한 키를 두 기능이 나눠 쓰는 구조 자체가 문제라, **셸에 기본 바인딩이 없는 조합**으로 옮겨 양쪽 충돌을 동시에 없앤다.

### How
- `src/components/Terminal.tsx`: 수락 분기를 Tab 핸들러에서 떼어 **`Shift`+`→`** 로 이동.
  - 가로채는 조건은 종전과 동일 — 제안이 존재하고(제안은 커서가 줄 끝일 때만 생긴다), 대체 화면(vim/less/tmux)이 아닐 것. 그 외에는 그대로 통과시켜 앱이 `\e[1;2C`를 받는다.
  - Tab은 **항상 셸 완성**으로 통과(#102의 원래 의도 복귀). Shift+Tab은 종전대로 역탭 `\e[Z`.
  - →/End 단독은 계속 순수 커서 이동(#127이 고친 것 유지).

### 함께 고친 문서 부채
#127이 동작만 바꾸고 안내를 갱신하지 않아 **실제와 다른 안내가 남아 있었다**:
- `Terminal.tsx`의 제안 힌트가 여전히 `→ {제안}` → `⇧→ {제안}` 으로 수정
- `README.md` — "accept with `→`/`End`" → `Shift + →`
- `docs/guide/shortcuts.md` — 표와 설명 문단 모두 갱신. "fish/zsh-autosuggestions 관행" 문구는 더 이상 맞지 않아(그쪽은 →) 왜 이 조합을 골랐는지로 바꿔 적었다.

### 후속 — 모디파이어+방향키가 쓰레기 문자를 찍던 문제
- 실사용 확인에서 발견. 제안이 없을 때 Shift+→를 셸로 통과시키면 xterm이 `\e[1;2C`를 보내는데 bash/zsh에 이 바인딩이 없다. 셸이 `\e[1`까지만 소비하고 나머지 **`;2C`를 리터럴로 삽입**한다.
- Shift+→만 막고 보니 **다른 조합도 전부 같은 증상**이었다 — `Shift+←`는 `;2D`, `Option+←`는 `;3D`, `Ctrl+←`는 `;5D`. 원래 방향키는 모디파이어와 무관하게 셸로 흘려보내고 있었다.
- 조치: 프롬프트(일반 화면)에서 **모디파이어 + 방향키를 전부 삼킨다**. 유일한 동작은 순수 Shift+→(제안이 있으면 수락, 없으면 무동작).
  - #112 선례(Option/Cmd+Delete를 readline 시퀀스로 번역)를 따라 **단어 이동·줄 처음/끝으로 매핑하는 안**도 검토했으나, 새 동작을 늘리지 않고 증상만 없애는 쪽으로 결정.
  - `⌘↑`/`⌘↓`(명령 단위 점프)는 이 블록보다 **앞에서** 처리되므로 영향 없음. 모디파이어 없는 방향키도 그대로.
  - 대체 화면 TUI(vim/less/tmux)는 이 시퀀스를 제대로 처리하므로 통과시킨다.
- **알려진 트레이드오프**: `Ctrl+←/→`(`\e[1;5D`/`C`)는 Linux의 bash·zsh에서 단어 이동으로 기본 바인딩된 경우가 많다. 지금은 이것도 삼키므로, 그런 서버에 SSH로 접속해 쓰던 사용자는 해당 키를 잃는다. 필요하면 Ctrl만 예외로 통과시킬 것.
- #139로 새로 생긴 문제는 아니다. 그전에도 방향키+모디파이어는 셸로 흘러가 같은 문자가 찍혔을 것 — Shift+→를 쓰라고 안내하면서 드러났을 뿐이다.

### 검증
- `tsc --noEmit` 통과. (Rust 변경 없음)
