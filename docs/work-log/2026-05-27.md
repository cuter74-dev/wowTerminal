## feat(ui) — S-011 터미널 화면 분할 (pane tree)

이슈: 미생성.

### 무엇을
- `Tab` 데이터 모델 재정의: `{ id, label, root: Pane, focusedPaneId }`. 기존 `source` 필드 제거.
- `Pane` 타입:
  ```ts
  type Pane =
    | { kind: "leaf"; id: string; source: TerminalSource }
    | { kind: "split"; direction: "vertical" | "horizontal"; ratio: number; first: Pane; second: Pane };
  ```
- 새 컴포넌트 `PaneView` — pane 트리를 재귀적으로 렌더, leaf는 헤더(라벨+×)+Terminal, split은 두 자식+드래그 구분선
- `types.ts`에 헬퍼: `findLeaf`, `collectLeaves`, `firstLeafId`, `splitLeaf`, `removeLeaf`, `setRatioByPath`, `neighborLeafId`
- App 액션: `splitActivePane(direction)`, `closePane(tabId, leafId)`, `focusPane`, `setPaneRatio`, `focusNeighborOrSwitchTab`
- 단축키:
  - `Ctrl+Shift+L` — 좌우 분할 (vertical)
  - `Ctrl+Shift+S` — 상하 분할 (horizontal). 와이어프레임은 `Ctrl+Shift+D`였으나 '탭 복제'와 충돌 → S로 이전
  - `Ctrl+Shift+방향키` — 분할이 있으면 인접 패널 포커스, 아니면 탭 좌/우 이동
- `TabContextMenu`의 "화면 분할 (좌우/상하)" 항목 실제 동작 연결
- `TabBar` / `TitleBar` / `AIPanel`을 새 데이터 모델에 맞춰 갱신:
  - 탭 아이콘: 단일 leaf면 source 기준, 분할이면 ⊟
  - AIPanel: 활성 탭에서 *포커스된 패널*의 source를 컨텍스트로 표시

### 왜
- 와이어프레임 명시: 한 탭 안에서 같은 호스트의 두 세션을 띄워 "한쪽은 로그 tail, 다른쪽은 명령 실행" 같은 패턴이 핵심 사용 흐름
- pane을 트리로 모델링한 이유: 재귀적 분할(나중에 nested split)이 자연스럽게 표현되고, 분할/병합 시 다른 leaf 상태(PTY 세션)에 영향이 없음
- leaf id를 React key로 쓰면 분할/병합 시 같은 leaf는 같은 컴포넌트 인스턴스 유지 → 세션 재spawn 방지
- `Ctrl+Shift+방향키`로 분할 시 패널 포커스 이동, 분할 없을 때 탭 이동으로 자동 fallback: 단일 단축키로 두 use case 처리 (사용자가 분할 여부를 의식하지 않아도 됨)

### 어떻게
1. `Pane` 트리 헬퍼 (`types.ts`)
   - `splitLeaf(root, targetId, newLeaf, direction)`: 대상 leaf를 split 노드로 교체, 첫 자식은 기존 leaf, 둘째는 새 leaf, ratio 0.5
   - `removeLeaf(root, targetId)`: 부모 split을 형제 leaf로 대체. root가 단일 leaf면 `null` (호출자가 탭 닫기로 위임)
   - `neighborLeafId(root, focusedId, direction)`: focused leaf의 조상 체인을 거슬러 올라가며 적합한 split을 찾고 반대편 자식의 첫/마지막 leaf로 점프
2. `PaneView` (`components/PaneView.tsx`)
   - leaf: 헤더(분할 시만) + Terminal. 포커스된 leaf는 1px 파란 outline + 헤더 배경 강조
   - split: flex 컨테이너(`flexDirection: row|column`) + 두 자식 + 4px 구분선
   - 구분선 드래그: mousedown → window mousemove → container rect 기준 ratio 계산 (최소 120px 보장) → mouseup으로 종료
3. App 흐름
   - `splitActivePane`: focused leaf의 source를 그대로 복사한 새 leaf로 분할. 포커스는 새 leaf로 이동
   - `closePane`: split 안의 leaf면 형제로 대체, 단일 leaf면 탭 자체 닫기로 위임
   - 호스트 단일 클릭 시 source 변경 대상은 focused leaf만. 다른 패널은 영향 없음

### 검증
- `npm run build` ✅ — 0 에러, 번들 560KB (gzip 155KB)
- 수동 GUI: 메뉴 "화면 분할 (좌우/상하)" / Ctrl+Shift+L / Ctrl+Shift+S → 분할 동작, 구분선 드래그 리사이즈, 패널 헤더의 × 클릭으로 닫기, 단일 leaf로 줄어들면 헤더 사라짐, Ctrl+Shift+방향키로 패널 포커스 이동 확인 필요.

### 메모 / 한계

### 왜
- 와이어프레임 S-008/009의 핵심 인터랙션 — 멀티 윈도우 없이는 "모니터 두 개에 prod/staging 따로 띄우기" 같은 패턴 불가.
- URL query 대신 `DetachedRegistry`로 source 전달한 이유: PathBuf+query string은 dev/prod 사이에서 인코딩 동작이 다르고 escape 이슈에 약함. 백엔드 in-memory registry + invoke 1회는 단순하고 확실.
- detached 여부를 *동기적으로* 알아야 한 이유: useState 초기값에서 결정하지 않으면 첫 탭이 임시로 spawn → kill → 새 source로 spawn하는 race가 생기고, 빠른 cleanup이 spawn 완료 전에 실행되면 좀비 PTY가 남을 수 있음.
- HTML5 native `draggable`을 쓴 이유: 드래그 ghost와 cursor 변경을 브라우저가 자동 처리. 커스텀 mouse tracker 대신 코드량 최소화.

### 어떻게
1. **백엔드**

   - `detached_init`: 항목을 *꺼내며 제거* — 윈도우 새로고침 시 재호출돼도 두 번째 호출은 None
2. **프론트엔드**
   - `IS_DETACHED_WINDOW` 상수: 모듈 top-level에서 `getCurrentWindow().label.startsWith("detached-")` 판단
   - `bootstrapped` state — detached면 false에서 시작, init effect 완료 시 true
   - `activeTabId` 타입을 `string | null`로 완화 (detached 부트 전에는 null). keyboard 핸들러에 null 가드 추가
   - `detachLeafToNewWindow(tabId)`: 지정 탭의 focused leaf source로 `open_detached_window` 호출 → 성공 시 원본 leaf/탭 close
   - 컨텍스트 메뉴 onDetach가 위 함수를 호출 (단독 leaf인 경우는 메뉴에서 비활성, 분할 leaf인 경우는 패널만 분리)
   - `<DropZoneOverlay>`: 탭바 아래 영역 전체 `position: fixed; inset: 66px 0 0 0`. `onDragOver=preventDefault`, `onDrop=getData(TAB_DRAG_MIME)`로 tabId 추출 후 detach
3. **capability**
   - `windows: ["main", "detached-*"]` glob 매처 사용. 새 윈도우도 같은 permission scope 받음

- 단독 탭 + 분할 트리는 메뉴 "새 창으로 분리"가 비활성 — 와이어프레임 규칙(`단독 탭일 때 새 창으로 분리 비활성`) 그대로. 단독 탭 + 분할일 때만 활성화하는 미세 조정은 후속
