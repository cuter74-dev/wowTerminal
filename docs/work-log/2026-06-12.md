## #96 — input dead after screen lock/sleep (esp. SSH): keepalive + closed detection + Enter-reconnect (v0.14.6)

GitHub #96 (English) / GitLab #15 (Korean).

- Cause: sleep kills the TCP connection; the app had no keepalive (russh `Config::default()`), the session actor just `break`s its loop on Eof/Close with **no event to the frontend**, and writes into the dead session are swallowed (`catch(() => {})`). Same blind spot for a local shell that exits.
- Fix:
  - russh `keepalive_interval=20s`, `keepalive_max=3` → dead peers detected within ~1 minute.
  - New `ClosedSink` (pty/manager.rs, shared type): the PTY reader thread and the SSH actor call it when the stream ends; both managers emit `session:closed {session_id}` (pty/commands.rs `SessionClosed`, ssh build_state wires the same event).

Enter while dead → `spawnFresh()` re-spawns in place; `onSshConnected` re-fires so host tmux auto-attach restores the session.

## #97 — paste re-inserted on the next keystroke (textarea residue × IME mirror) (v0.14.7)

GitHub #97 (English) / GitLab #16 (Korean). User report: "카피한 후 붙여넣기 하고 다음에 타자를 치면 붙여넣기가 또 되는 버그".

- Cause (proven from the bundled xterm source, not guessed): `handlePasteEvent` calls `e.stopPropagation()` but **not `preventDefault()`** — xterm sends the clipboard text to the PTY itself, but WebKit's default action *also* inserts it into the hidden helper textarea. The residue sits there invisibly; the next keyCode-229 keydown engages the custom IME mirror, which diffs the textarea against its empty `imeSent` baseline and re-sends the residue to the PTY → paste appears twice.
- Fix (Terminal.tsx, two layers):
  1. When the mirror engages (first 229 while not active), it snapshots the current textarea content as the diff baseline (`imeSent = ta.value`) instead of assuming empty — any pre-existing residue is never re-sent.
  2. A `paste` listener on the textarea clears the residue on the next tick (when the mirror isn't mid-composition), so the textarea doesn't accumulate paste junk at all.
- Regression test: self-test scenario T4 (`src/inputSelfTest.ts`) — dispatch a paste ClipboardEvent with `PB123`, simulate WebKit's default insertion into the textarea (synthetic events have no default actions), then type Korean `가` through the mirror; assert the shell file is `PB123가` (paste exactly once).
- **Input gate passed on this build**: T1 `st-en-abcxyz` / T2 `안녕` / T3 `가나` / T4 `PB123가`, residue `[]`.

## #100 — macOS Korean broken on composition-capable Macs (mirror vs native IME) (v0.14.10)

GitHub #100 (English) / GitLab #19 (Korean). Maintainer on v0.14.9 installed app: "한글이 제대로 안 써지고 영어로 바꾸었다 다시 한글로 바꾸었다 하면 삭제도 제대로 안돼." This is the standing-order input path, so I read the real data first — no guessing.

- **Diagnosis from live data, not theory.** The installed app's `wt.ime.local-diag` (read via the `com.wowterminal.app` WKWebView sqlite): `nCS:15, nCU:33, nCE:15, n229:19, mirrorChars:4`. **Composition events fire for Korean on this Mac** — the opposite of the maintainer's dev machine (`nCS:0`, pure 229), which is the entire reason the custom mirror exists. So this machine has two input handlers fighting.
- **Mechanism** (three coupled bugs):
  1. The first keyCode-229 of each syllable engages the mirror (`imeActive=true`) before `compositionstart` flips `nativeComposition`, so the mirror sends stray chars → "한글이 제대로 안 써짐" (`mirrorChars:4`).
  2. `imeActive` lingers into English mode; the keydown handler's `if (imeActive)` branch `return false`s a Backspace expecting a mirror `input` that never comes → swallowed deletion.
  3. `compositionstart`'s `resetIme()` clears `ta.value` mid-composition, corrupting the syllable the native IME is composing.
- **Fix** (Terminal.tsx): detect a composition-capable Mac by a **Hangul-committing composition** — `compositionupdate/end` data matching `[ᄀ-ᇿ㄰-㆏가-힣]`. A 229-only Mac never produces this; accent-popup/dictation commit Latin so they never trip it (avoids the v0.14.3 "single stray composition disables the mirror forever" regression). Latch `compositionMachine` (persisted to `localStorage["wt.ime.cmp"]`): keyCode-229 then always yields to native, the mirror never engages, and `compositionstart` no longer touches `ta.value`. 229-only Macs are unchanged (flag never set → mirror as before).
- **Harness gap closed (this is why it passed while real input broke).** The old harness only drove the mirror path (synthetic 229 + textarea transitions) and never dispatched composition events, so it could not see a composition machine. New **T5** dispatches the real composition sequence (`compositionstart`→`compositionupdate`→`input`→`compositionend` with Hangul), then sends a lone 229 (no following composition) + English `st5-del` → BS×3 → `xyz`, asserting `/tmp/wt-st5.txt` == `st5-xyz`. On the old code the lone 229 sticks `imeActive` and the Backspaces are swallowed → file wrong; only the fix yields `st5-xyz`. T5 backs up/restores `wt.ime.cmp` so it can't contaminate a real machine (verified: flag `None` after the gate).
- **Gate passed**: T1 `st-en-abcxyz` / T2 `안녕` / T3 `가나` / T4 `PB123가` / T5 `st5-xyz`.
- **Honest caveat to the maintainer**: synthetic events can verify the mirror path and this state machine, but cannot fully reproduce a real macOS IME end-to-end (xterm's native composition needs a real IME to emit onData). Real-machine confirmation requested before closing #100.

## #100 cont. — "Backspace=Space" root cause from the diagnostic: IME commits non-breaking space (v0.14.13)

Maintainer reproduced on the signed 0.14.12 (composition machine). Read the `input`/`kd` rings from GlitchTip (build `ci.1ba03a7`):
- `input` (bytes sent to PTY): `r,k,s,k, \x7f×5, 가,나,아,다,라\xa0, \x7f×6` — every `Backspace/8` keydown produced **`\x7f`** (the correct delete byte). So Backspace is NOT sending the wrong byte.
- `lines` (xterm buffer): `cwjung@cwM1max ~ % rksk    가나아다라\xa0` — a **bare zsh** (not Claude Code), and the typed text is still present after the backspaces, with stray spaces. So xterm's *buffer model* is wrong, not just the pixels → not a renderer-only issue.
- The smoking gun: `라\xa0` and `' /229'` — the **Space key is committed as U+00A0 (non-breaking space)** by macOS inline predictive text (our `writingsuggestions=false` doesn't fully stop it here, consistent with #83).

- **Fix** (Terminal.tsx): normalize ` ` → regular space on input, on both the native onData path (the reported composition-machine case) and the mirror `flushMirror` path. A terminal Space must be `\x20`.
- Harness **T6**: type `echo st6<U+00A0>ok` and assert the shell receives `st6 ok` (regular space). Unfixed → the nbsp reaches the shell and the file mismatches.

## #101 — Windows/Linux copy/paste keyboard shortcuts (v0.15.0)

GitHub #101 (English) / GitLab #20 (Korean). Maintainer asked whether Ctrl+C/Ctrl+V could work on Windows (only ⌘C/⌘V existed, macOS-only; on Windows copy was select → right-click → context menu).

- The conflict: in a terminal Ctrl+C is SIGINT, so it can't be a blanket "copy". Solution (Windows Terminal / VS Code): **Ctrl+C copies when there is a selection, otherwise SIGINT** — the exact pattern the macOS ⌘C handler already uses.
- Added to `attachCustomKeyEventHandler` (Terminal.tsx), scoped `!isMacWebView` so macOS ⌘C/⌘V are untouched:
  - **Ctrl+C**: `hasSelection` → copy + `preventDefault` + return false; else `return !e.shiftKey` (Ctrl+C passes through to SIGINT, Ctrl+Shift+C consumed/no-op).
  - **Ctrl+V / Ctrl+Shift+V**: `navigator.clipboard.readText()` → `term.paste(text)` (honors bracketed-paste mode) + return false.
- Verified the App capture-phase shortcut handler (#92) doesn't bind C/V (defaults are t/w/Tab/l/s/d/F2/b/j), so the events reach the terminal handler.
- Gate runs on macOS (the `!isMacWebView` branches don't execute there), so it only confirms no macOS regression; the Windows behavior must be confirmed on Windows by the maintainer.
