## #84 — Korean input completely broken on Windows (v0.13.0 regression)

GitHub #84 (English) / GitLab #3 (Korean).

### What / Why / How
- Symptom: after v0.13.0, Hangul could not be typed at all on Windows.
- Cause: the #83 IME fix added a `compositionstart` → `nativeComposition` bypass that disables the custom IME mirror and lets xterm handle IME natively. It targeted the newest macOS WKWebView, but **Windows WebView2 (Chromium) always fires composition events**, so the bypass triggered there too — disabling the mirror that Windows depends on, and xterm's native path doesn't input Korean on Windows.
- Fix (`Terminal.tsx`): gate the bypass to macOS only via `const isMacWebView = navigator.userAgent.includes("Mac")`. The `compositionstart` listener is registered only when `isMacWebView`; on Windows/Linux `nativeComposition` stays false, so the keyCode-229 path keeps using the custom mirror exactly as in v0.12.0. macOS keeps the newest-WKWebView bypass from #83.
- `npm run build` ✅. Windows fix is logically a restoration of the pre-#83 path (mirror) — verified by reasoning; macOS path unchanged.

## #85 — Terminal output freezes after a command (v0.13.0 regression)

GitHub #85 (English) / GitLab #4 (Korean).

### What / Why / How
- Symptom: on the local shell, after any command (e.g. `pwd`) output stops rendering and the terminal looks frozen. Input still reaches the shell.
- Diagnosis (this is where the new GlitchTip telemetry paid off — it captured the exact error): `Error: You must set the allowProposedApi option to true to use proposed API`. The OSC 133 command-badge code calls `term.registerDecoration()`/`term.registerMarker()` (xterm proposed API); without `allowProposedApi: true` they throw inside the OSC 133 handler, breaking xterm's write/parse loop → all subsequent output swallowed. Triggered from v0.13.0 because `npm install @sentry/react` (#82) re-resolved `@xterm/xterm` (^6.0.0) to a build that enforces proposed-API gating.
- Confirmed input vs output via temporary Rust logging: keystrokes reach the PTY and the shell echoes them (`[pty.out] emit`), but the frontend didn't render — output-display freeze, not input.
- Fix (`Terminal.tsx`): add `allowProposedApi: true` to the xterm constructor; wrap the OSC 133 handler in try/catch so a future badge/marker error degrades gracefully instead of freezing the terminal. Removed the temporary Rust logs.
- Also: the command badge hides the duration for near-instant commands (< 100ms), showing just `✓`/`✗` instead of a noisy `0ms` (the timer itself is correct — `sleep 2` → `✓ 2.0s`).

## #86 — Terminal ghosting on window shrink+grow; #83 M5 IME remote diagnostics

GitHub #86 (English) / GitLab #5 (Korean).

### #86 — resize ghosting
- Symptom (screen recording): shrinking the window very small then enlarging it leaves the terminal garbled — the prompt split vertically one char per line, narrow-wrapped scrollback persists as ghosting.
- Cause: FitAddon shrank the terminal to ~2 columns; zsh re-rendered its prompt at that width and the hard-wrapped lines stayed in scrollback (no reflow on grow).
- Fix (`Terminal.tsx`): `safeFit` clamps cols/rows to a minimum (20x4) via `proposeDimensions` + `term.resize` instead of raw `fit.fit()`. Added `overflow: hidden` to the terminal wrapper + container so that when the container is narrower than the min width, the terminal clips instead of overlapping the AI panel.

## #83 follow-up 2 — IME diagnostic delivery bug (v0.13.4)

- After v0.13.3, the M5 user confirmed v0.13.3 + typed `df -h` but no `wt-ime-diag` event arrived at GlitchTip. Investigation: no PRODUCTION-environment event has ever reached GlitchTip (all were `development`). Ruled out CSP (null) and CORS (the ingest returns `Access-Control-Allow-Origin: *`, incl. preflight for `Origin: tauri://localhost`), and main.tsx has no prod gating.
- Root cause = a bug in my own diagnostic: `sendImeDiag()` was called from the onData Enter branch, but onData early-returns while `imeActive` is true (the IME mirror is active). On the M5 machine the mirror is active for the duplicating input, so Enter never reached the send. Fix: trigger `sendImeDiag()` from `attachCustomKeyEventHandler` on Enter (runs regardless of imeActive), and broaden the send gate to fire on the first line with any input via any path (229/composition/mirror/onData), not just IME-gated.
- v0.13.4 is diagnostic-delivery-only (no user-facing change). Once the M5 trace lands, fix the duplication and remove the instrumentation.

## #83 fix — WebGL renderer (v0.13.6)

### What / Why / How
- Conclusion from the diagnostics + user reports: the M5 `df -h` → `dddff f -h` is a **display/render bug, not input**. The bytes written to the PTY are correct (commands run correctly; `cat` shows clean text; Terminal.app is clean). It only appears at the **zsh prompt** with **oh-my-zsh** plugins (syntax-highlighting) that redraw the whole input line on each keystroke. xterm's **DOM renderer** on the newest macOS WKWebView doesn't clear the previous glyphs on that redraw, so the line accumulates ghosted characters.
- Fix (`Terminal.tsx`): load `@xterm/addon-webgl` after `term.open()`. The WebGL renderer repaints the entire viewport each frame, so a line redraw leaves no stale glyphs. `onContextLoss` disposes the addon → xterm falls back to the DOM renderer; the `loadAddon` is wrapped in try/catch so any WebGL-unavailable environment silently keeps the DOM renderer. The change affects all platforms (GPU-accelerated rendering), so verified locally with a release build that the terminal renders correctly before shipping.
- Removed all the temporary `[임시 진단]` IME instrumentation (the `imeDiag` counters, `sendImeDiag`/`scheduleImeDiag`, the `wt-ime-diag` GlitchTip send, and the `@sentry/react` import in `Terminal.tsx`) now that the cause is identified and fixed. Frontend Sentry in `main.tsx` stays.
- `npm run build` ✅, `npm run tauri build --no-bundle` ✅, launched the release binary — renders fine on the maintainer's machine.

## #87 — Keyboard tab switch doesn't focus the terminal

GitHub #87 (English) / GitLab #6 (Korean).

### What / Why / How
- Symptom: switching tabs with Ctrl+Tab / Ctrl+Shift+Tab / Ctrl+number moves focus to the tab but the terminal stays unfocused — you must click the terminal before keystrokes register.
- Cause: the tab switch handlers only call `setActiveTabId`; nothing gives the newly shown terminal keyboard focus.
- Fix: `TerminalHandle` gains `focus()` (`term.focus()`), registered in `Terminal.tsx`. The tab-activation effect in `App.tsx` (already re-fits all leaves of the active tab in a rAF) now also calls `focus()` on the active tab's `focusedPaneId` leaf in the same rAF, after the panes are visible/registered. `npm run build` ✅.
