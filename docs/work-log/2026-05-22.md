## #2 — OpenAI 호환 AI 어댑터 구현

이슈: https://github.com/cuter74-dev/wowTerminal/issues/2

### 무엇을
- `AiBackend` 트레잇의 첫 구현체로 `OpenAiCompatibleBackend` 작성.
- 다중 백엔드 관리용 `AiRegistry` (id → 구현체 매핑).
- 백엔드 설정 데이터 모델 `BackendConfig` / `OpenAiCompatibleConfig`.
- 프론트엔드용 Tauri command `ai_list_backends`, `ai_complete`.
- HTTP 클라이언트(`reqwest` rustls), URL/UUID 의존성 추가.
- `wiremock` 기반 단위/통합 테스트 9개 추가, 모두 통과.

### 왜
- 첫 어댑터를 "OpenAI 호환"으로 선택한 이유는 **하나의 코드로 외부(OpenAI 본가) + 자체 호스팅(vLLM/TGI/Together) + 로컬(Ollama OpenAI 엔드포인트)을 동시에 커버**할 수 있기 때문이다. 어댑터 수를 늘리지 않고 가장 많은 환경을 지원.
- `AiRegistry`를 도입한 이유: 프론트는 `backend_id` 문자열로만 백엔드를 지정하고, 백엔드 인스턴스의 라이프사이클/락은 백엔드 코드 한 곳에서만 관리되도록 책임 분리.

### 어떻게
1. **의존성 추가** (`src-tauri/Cargo.toml`)
   - `reqwest = { version = "0.12", default-features = false, features = ["rustls-tls", "json", "stream"] }`
   - `url`, `uuid`(v4), `futures-util`
   - `[dev-dependencies]`: `wiremock = "0.6"`, `tokio` macros/test-util.
2. **모듈 구조**
   ```
   src-tauri/src/ai/
   ├── mod.rs              # AiBackend 트레잇, prelude
   ├── types.rs            # Message/ChatRequest/ChatResponse/AiError/TokenUsage
   ├── config.rs           # BackendConfig (enum) + OpenAiCompatibleConfig
   ├── registry.rs         # AiRegistry: HashMap<String, Arc<dyn AiBackend>>
   ├── commands.rs         # Tauri command: ai_list_backends, ai_complete
   └── adapters/
       ├── mod.rs
       └── openai_compat.rs   # OpenAiCompatibleBackend
   ```
3. **어댑터 구현 포인트**
   - 외부 도메인 모델(`ChatRequest`/`ChatResponse`)과 OpenAI wire format(`OpenAiChatRequest`/`OpenAiChatResponse`)을 분리해 어댑터가 변환 담당.
   - HTTP 401/403 → `AiError::Auth`, 429 → `AiError::RateLimited`, 5xx → `AiError::Backend("server ...")`.
   - `api_key`가 `None`이면 `Authorization` 헤더를 생략 (인증 불필요 로컬 서버 지원).
4. **레지스트리**
   - `Arc<RwLock<HashMap<String, Arc<dyn AiBackend>>>>` 로 멀티스레드 안전.
   - `complete()`은 RwLock의 read guard에서 `Arc<dyn AiBackend>` clone 후 락 해제 → trait 호출.
5. **Tauri 통합**
   - `lib.rs`의 `Builder::default()`에 `.manage(AiRegistry::new())` 추가.
   - `invoke_handler`에 `ai_list_backends`, `ai_complete` 등록.
6. **검증**
   - `cargo check` ✅
   - `cargo test --lib` ✅ (9 passed, 0 failed)
     - happy path JSON 파싱
     - 401 → Auth, 429 → RateLimited, 503 → Backend
     - choices 비어있을 때 → InvalidResponse
     - api_key None일 때 헤더 미포함
     - 레지스트리 register/list/dispatch
     - 알 수 없는 backend_id → Backend 에러
     - 레지스트리 + OpenAI 호환 어댑터 + wiremock 통합

### 메모
- 스트리밍(`complete_stream`)은 다음 단계로 미룸. 백엔드 단의 SSE 파서 + Tauri event 송신을 함께 설계해야 의미가 있어서 PTY 작업과 묶는 게 좋음.
- Anthropic은 별도 어댑터 필요 (응답 포맷이 OpenAI와 다름). 다음 어댑터 작업 때.

## #3 — Secret store: keyring + Argon2id/AES-256-GCM 파일 폴백

이슈: https://github.com/cuter74-dev/wowTerminal/issues/3

### 무엇을
- `SecretStore` 트레잇 + 두 구현체:
  - `KeyringStore`: OS 키링 (libsecret / Keychain / Credential Manager)
  - `EncryptedFileStore`: 사용자 패스프레이즈로 AES-256-GCM 암호화한 TOML 파일
- 평문 시크릿은 항상 `Zeroizing<Vec<u8>>`로 다뤄 drop 시 자동 zeroize.
- 단위 테스트 6개 추가 (모두 통과).

### 왜
- API 키/SSH 패스프레이즈/비밀번호 같은 시크릿을 **`backends.toml`/`hosts.toml`에 절대 평문으로 두지 않는** CLAUDE.md 보안 규칙을 만족해야 한다.
- 1순위로 OS 키링을 두는 이유: 가장 견고하고, 사용자가 별도 패스프레이즈를 외울 필요가 없음.
- 2순위로 패스프레이즈 파일을 두는 이유: 헤드리스 Linux / SSH-only 환경 / 키링 비활성 환경에서도 동작해야 함.
- AAD에 `id`를 묶은 이유: 공격자가 디스크 파일을 수정해 서로 다른 시크릿의 ciphertext를 바꿔치기하는 시나리오를 차단 (AAD 불일치로 AEAD 실패).

### 어떻게
1. **의존성** (`Cargo.toml`)
   - `keyring = "3"` (Linux: sync-secret-service, macOS: apple-native, Windows: windows-native)
   - `aes-gcm = "0.10"`, `argon2 = "0.5"`, `rand = "0.8"`, `zeroize`, `base64`, `toml`
2. **모듈 구조**
   ```
   src-tauri/src/secrets/
   ├── mod.rs              # SecretStore trait + SecretError + Secret(Zeroizing)
   ├── keyring_store.rs    # KeyringStore
   └── encrypted_file.rs   # EncryptedFileStore (TOML on-disk format)
   ```
3. **디스크 형식 (`EncryptedFileStore`)**
   - `version`, `salt` (file 전체에서 1개의 Argon2id 솔트), `[entries.<id>]` 테이블에 `nonce` + `ciphertext` (둘 다 base64).
   - 키 유도: `Argon2id(passphrase, salt, params=m:64MiB/t:3/p:1, 32B 출력)`.
   - 시크릿마다 `nonce = OsRng.fill(12B)`; `ct = AES-256-GCM(kek, nonce, plaintext, aad=id)`.
4. **에러 매핑**
   - AEAD 실패 (패스프레이즈 틀림 / 디스크 변조)는 모두 `SecretError::BadPassphrase` 단일 변환자로 매핑 — 외부에서 두 경우를 구분 못 하도록.
5. **검증**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **15 passed** (기존 9 + 신규 6)
     - roundtrip / overwrite / delete (없는 키 삭제도 OK)
     - 잘못된 패스프레이즈로 재오픈 → `BadPassphrase`
     - ciphertext 1바이트 변조 → `BadPassphrase`
     - id A의 ciphertext를 id B 자리에 두면 AAD 불일치로 `BadPassphrase`

### 메모
- `KeyringStore`는 헤드리스 환경에서 Secret Service가 없으면 사용 불가. 통합 코드에서 키링 시도 → 실패 시 `EncryptedFileStore`로 폴백하는 `CompositeStore`는 다음 단계에서 도입 예정 (사용자 설정에서 강제 선택도 가능하게).
- `keyring` crate은 문자열만 받기 때문에 임의 바이트는 base64로 인코딩해 저장 (load 시 복원).
- AEAD 실패 에러를 `BadPassphrase`로 통일했지만 실제로는 "잘못된 키" + "변조된 데이터" 둘 다일 수 있음. 사용자에게는 둘 다 동일한 액션(패스프레이즈 재입력)이 자연스러우므로 OK.
