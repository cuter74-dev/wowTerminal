## #3 — Secret store: keyring + Argon2id/AES-256-GCM 파일 폴백

이슈: https://github.com/cuter74-dev/wowTerminal/issues/3

### 무엇을
- `SecretStore` 트레잇 + 두 구현체:
  - `KeyringStore`: OS 키링 (libsecret / Keychain / Credential Manager)
  - `EncryptedFileStore`: 사용자 패스프레이즈로 AES-256-GCM 암호화한 TOML 파일
- 평문 시크릿은 항상 `Zeroizing<Vec<u8>>`로 다뤄 drop 시 자동 zeroize.
- 단위 테스트 6개 추가 (모두 통과).

### 왜
- API 키/SSH 패스프레이즈/비밀번호 같은 시크릿을 **`backends.toml`/`hosts.toml`에 절대 평문으로 두지 않는** CLAUDE.md 보안 규칙을 만족해야 한다.
- 1순위로 OS 키링을 두는 이유: 가장 견고하고, 사용자가 별도 패스프레이즈를 외울 필요가 없음.
- 2순위로 패스프레이즈 파일을 두는 이유: 헤드리스 Linux / SSH-only 환경 / 키링 비활성 환경에서도 동작해야 함.
- AAD에 `id`를 묶은 이유: 공격자가 디스크 파일을 수정해 서로 다른 시크릿의 ciphertext를 바꿔치기하는 시나리오를 차단 (AAD 불일치로 AEAD 실패).

### 어떻게
1. **의존성** (`Cargo.toml`)
   - `keyring = "3"` (Linux: sync-secret-service, macOS: apple-native, Windows: windows-native)
   - `aes-gcm = "0.10"`, `argon2 = "0.5"`, `rand = "0.8"`, `zeroize`, `base64`, `toml`
2. **모듈 구조**
   ```
   src-tauri/src/secrets/
   ├── mod.rs              # SecretStore trait + SecretError + Secret(Zeroizing)
   ├── keyring_store.rs    # KeyringStore
   └── encrypted_file.rs   # EncryptedFileStore (TOML on-disk format)
   ```
3. **디스크 형식 (`EncryptedFileStore`)**
   - `version`, `salt` (file 전체에서 1개의 Argon2id 솔트), `[entries.<id>]` 테이블에 `nonce` + `ciphertext` (둘 다 base64).
   - 키 유도: `Argon2id(passphrase, salt, params=m:64MiB/t:3/p:1, 32B 출력)`.
   - 시크릿마다 `nonce = OsRng.fill(12B)`; `ct = AES-256-GCM(kek, nonce, plaintext, aad=id)`.
4. **에러 매핑**
   - AEAD 실패 (패스프레이즈 틀림 / 디스크 변조)는 모두 `SecretError::BadPassphrase` 단일 변환자로 매핑 — 외부에서 두 경우를 구분 못 하도록.
5. **검증**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **15 passed** (기존 9 + 신규 6)
     - roundtrip / overwrite / delete (없는 키 삭제도 OK)
     - 잘못된 패스프레이즈로 재오픈 → `BadPassphrase`
     - ciphertext 1바이트 변조 → `BadPassphrase`
     - id A의 ciphertext를 id B 자리에 두면 AAD 불일치로 `BadPassphrase`

### 메모
- `KeyringStore`는 헤드리스 환경에서 Secret Service가 없으면 사용 불가. 통합 코드에서 키링 시도 → 실패 시 `EncryptedFileStore`로 폴백하는 `CompositeStore`는 다음 단계에서 도입 예정 (사용자 설정에서 강제 선택도 가능하게).
- `keyring` crate은 문자열만 받기 때문에 임의 바이트는 base64로 인코딩해 저장 (load 시 복원).
- AEAD 실패 에러를 `BadPassphrase`로 통일했지만 실제로는 "잘못된 키" + "변조된 데이터" 둘 다일 수 있음. 사용자에게는 둘 다 동일한 액션(패스프레이즈 재입력)이 자연스러우므로 OK.

## #4 — 로컬 PTY + xterm.js 터미널

이슈: https://github.com/cuter74-dev/wowTerminal/issues/4

### 무엇을
- Rust: `portable-pty` 기반 `PtyManager` (spawn/write/resize/kill) + reader 스레드 → 콜백 sink
- Tauri command: `pty_spawn`, `pty_write`, `pty_resize`, `pty_kill`
- Tauri event: `pty:output { session_id, data_b64 }`
- 프론트: `@xterm/xterm`, `@xterm/addon-fit` 사용한 `<Terminal>` 컴포넌트
- `App.tsx`를 풀스크린 터미널 1개로 교체
- PTY 단위 테스트 4개 추가 (모두 통과, 총 19개)

### 왜
- 터미널 앱의 본질은 결국 "PTY ↔ 터미널 렌더러". 이 골격이 동작해야 SSH 채널이든 컨테이너든 다음 단계에서 같은 stream 인터페이스로 붙일 수 있다.
- 데이터 전달 추상화를 `DataSink` (`Arc<dyn Fn(SessionId, Vec<u8>)>`) 콜백으로 만든 이유: Tauri event emit이 없는 테스트 환경에서도 spawn → write → 출력 검증을 할 수 있어야 함. 실제 앱에서는 `build_manager(&app)`에서 sink가 `app.emit("pty:output", ...)`로 연결됨.
- bytes를 base64로 감싼 이유: PTY 출력은 임의 바이트(8-bit, non-UTF8 가능)인데 Tauri의 `serde_json` 채널은 valid UTF-8이 필요. base64는 JSON-safe하면서 ~33% overhead로 충분히 가볍다.

### 어떻게
1. **Rust 측 의존성** (`portable-pty = "0.9"`)
2. **모듈 구조**
   ```
   src-tauri/src/pty/
   ├── mod.rs              # 공개 API (PtyManager, SessionId, PtyError)
   ├── manager.rs          # 코어 매니저 + DataSink 추상, 단위 테스트
   └── commands.rs         # Tauri command + event emit sink 생성
   ```
3. **`PtyManager` 동작**
   - `spawn(program, dims)`: `native_pty_system().openpty(...)` → `slave.spawn_command(...)` → master writer/reader 분리. reader는 별도 OS thread에서 read 루프 → `(sink)(session_id, bytes)`.
   - `write` / `resize` / `kill`: `Mutex<HashMap<SessionId, Session>>`에서 lookup 후 위임. 없는 id는 `PtyError::NotFound`.
4. **Tauri 통합** (`lib.rs`)
   - `.setup` 클로저에서 `build_manager(&app.handle())`로 매니저 생성 (sink가 `app.emit("pty:output", payload)` 클로저).
   - `app.manage(PtyState(manager))` 등록. `pty_*` command들 invoke_handler에 추가.
5. **프론트엔드** (`src/components/Terminal.tsx`)
   - `@xterm/xterm` + `addon-fit`로 컨테이너에 부착, `ResizeObserver`로 사이즈 추적.
   - `term.onData(s)` → `pty_write({sessionId, dataB64: base64(utf8(s))})`.
   - `listen("pty:output", ...)` → `term.write(base64decode(payload.data_b64))`.
   - `useEffect` cleanup에서 dispose + `pty_kill` 호출.
6. **검증**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **19 passed** (기존 15 + 신규 4)
     - `/bin/sh`로 `echo wowterm-hello\nexit\n` 보내고 sink에서 marker 수신 확인 (라인 에코 + 셸 echo 양쪽 다 포함되므로 안정적)
     - 없는 세션에 resize/write → NotFound
     - kill 후 session_count == 0
   - `npm run build` ✅ — TypeScript + Vite production build, 0 에러

### 메모 / 한계
- 실제 GUI(`npm run tauri dev`)는 디스플레이 서버가 필요해서 헤드리스 환경에서는 자동 검증 불가. 비-GUI 검증(cargo test + npm build)으로 마무리하고, 화면에서의 키 입력/출력 확인은 사용자가 별도로.
- `xterm` 패키지가 deprecated → `@xterm/xterm`으로 교체.
- 데이터 sink가 콜백 기반이라 비싼 sync emit(매 read마다)이 부담될 수 있음. 추후 mpsc + spawn된 tokio task에서 batch emit으로 최적화 여지 있음. 현 단계에서는 가장 단순한 동작 우선.

## #5 — SSH 매니저: russh + hosts.toml + 호스트 UI

이슈: https://github.com/cuter74-dev/wowTerminal/issues/5

### 무엇을
- Rust 모듈 `src-tauri/src/ssh/`
  - `store.rs` — `HostStore`: `hosts.toml` CRUD
  - `session.rs` — `SshSession`: russh 0.61 클라이언트, PTY 채널, actor 패턴
  - `manager.rs` — `SshManager`: 활성 세션 HashMap
  - `commands.rs` — `ssh_list_hosts` / `ssh_save_host` / `ssh_delete_host` / `ssh_connect` / `ssh_write` / `ssh_resize` / `ssh_kill`
  - 이벤트: `ssh:output` (PTY와 동일 포맷, base64 페이로드)
- 프론트엔드
  - `src/types.ts` — `SshHost`/`SshAuthMethod`/`TerminalSource` 타입
  - `<HostList>` — 사이드바: Local shell + SSH 호스트 목록, 편집/삭제 아이콘, "+ 새 호스트"
  - `<HostForm>` — 모달: name/host/port/user + auth(agent/password/private_key)
  - `<Terminal>` 컴포넌트가 `source` prop을 받아 local PTY/SSH 분기 처리
- 단위 테스트 10개 추가 (호스트 스토어 5, 세션 보조 5).

### 왜
- 사용자 시나리오 "호스트 클릭 한 번에 SSH 접속"을 완성하려면 호스트 저장 + 인증 + 채널 + UI를 모두 갖춰야 의미가 있다. 한 이슈에 묶었다.
- 호스트 메타데이터(`hosts.toml`)와 시크릿을 분리한 이유: 메타는 사용자가 export/공유 가능해야 하지만 시크릿은 절대 동봉되면 안 됨. `*_secret_id` 참조로 디커플링.
- SSH 세션을 actor 태스크 + `mpsc` 명령 채널로 만든 이유: russh 0.61의 `Channel`은 `wait()`로 메시지를 수신하는 형태라 한 스레드/태스크가 owning해야 함. 외부에서 `data()` / `window_change()` / `close()`를 호출하려면 채널 자체를 보내거나, 명령을 보내야 함. 후자가 더 깔끔.
- 호스트 키 검증은 v1에서 무조건 수락(`PermissiveHandler`). 보안상 추후 known_hosts TOFU 도입 필요 — 코드에 TODO로 표시.

### 어떻게
1. **의존성** (`Cargo.toml`)
   - `russh = "0.61"`, `dirs = "5"`, `tempfile = "3"` (테스트용)
2. **세션 액터 패턴**
   ```rust
   enum SessionCmd { Write(Vec<u8>), Resize { cols, rows }, Close }
   ```
   `tokio::spawn`된 태스크에서 `tokio::select!`로 cmd 수신 / 채널 메시지 처리. `data()` / `window_change()` / `eof()`+`close()`로 매핑. 외부 `SshSession::write/resize/close`는 mpsc send만 함.
3. **인증 흐름** (`ResolvedAuth::from_method`)
   - `Password` → `SecretStore::load(secret_id)` → UTF-8 검증 → russh `authenticate_password`
   - `PrivateKey` → key PEM + (optional) passphrase → `PrivateKey::from_openssh` (+ decrypt) → russh `authenticate_publickey`
   - `Agent` → v1 미구현. 명시적 에러.
   - `Debug`는 시크릿 노출 방지 위해 `<redacted>`로 수동 구현.
4. **Tauri State 구조**
   - `SshState { manager, store, secrets: Option<Arc<dyn SecretStore>> }`
   - secrets는 v1에서 unlock 흐름 미완성 — 상태에 None으로 두고, `secrets_unlock` 커맨드는 "not implemented yet" 반환.
5. **프론트엔드 통합**
   - `<Terminal source={...}>`로 일반화. local이면 `pty_*` + `pty:output`, ssh면 `ssh_*` + `ssh:output`을 dispatch하는 헬퍼 `commandsFor`.
   - `<HostList>`에서 source 변경 → Terminal 컴포넌트가 `sourceKey` 변경을 감지해 cleanup + 새 세션 시작.
6. **검증**
   - `cargo check` ✅ (warning 0)
   - `cargo test --lib` ✅ — **29 passed** (PTY 4 + AI 9 + Secrets 6 + SSH store 5 + SSH session 5)
     - SSH store: empty/upsert+list/upsert 갱신/delete 멱등 아님/auth method 3종 serde 라운드트립
     - SSH session: 닫힌 포트에 connect 시 Connect 또는 Auth 에러 (5초 timeout 안에 실패), ResolvedAuth password missing→Auth/utf8 디코드/Agent NotImplemented/잘못된 PEM 파싱 실패
   - `npm run build` ✅ — TS+Vite 무에러
   - **수동 GUI 검증은 후속** — 디스플레이가 있는 환경에서 `npm run tauri dev`로 호스트 추가 → 접속 시도까지 확인 필요.

### 메모 / 한계
- russh 0.61 API는 0.45 대비 큰 폭으로 변경 (Channel 위주, async fn in trait, `keys::PrivateKey` 등). 이전 가이드들과 시그니처가 많이 다르니 마이그레이션 시 주의.

- 호스트 키 검증은 TOFU 미구현 — MITM 위험. 1.0 전 반드시 도입 필요.
- 번들 크기 534 KB (gzip 148 KB) — code-splitting은 추후.

## #6 — 보안: known_hosts TOFU 도입

이슈: https://github.com/cuter74-dev/wowTerminal/issues/6

### 무엇을
- `KnownHostsStore` (`src-tauri/src/ssh/known_hosts.rs`) — `host:port → {algorithm, fingerprint, added_at}` 매핑, TOML 파일 (`~/.config/wowterminal/known_hosts.toml`)
- `TofuHandler`가 `PermissiveHandler`를 대체. `russh::Handler::check_server_key`에서:
  - 첫 접속: 저장 + 수락
  - 일치: 수락
  - 불일치: 거절 + `TofuOutcome::Mismatch` 기록
- `SshError::HostKeyMismatch { host, port, stored, presented }` 추가. session connect가 실패할 때 outcome을 확인해 일반 Connect 에러 대신 이 명확한 에러로 변환.
- Tauri commands 3개 추가: `ssh_list_known_hosts`, `ssh_forget_known_host`, `ssh_trust_known_host(host, port, algorithm, fingerprint)`
- `SshState`/`build_state`/`lib.rs setup`이 `known_hosts.toml` 경로를 받아 store를 매니저와 공유하도록 갱신.
- `docs/design/ssh-manager.md`에 정책/형식/한계 명시.
- 단위 테스트 10개 추가 (KnownHostsStore 6 + TofuHandler 4). 전체 **39 passed**.

### 왜
- 기존 `PermissiveHandler`는 임의의 서버 키를 수락 → MITM 시 사용자가 사칭된 서버로 자격증명 전송할 위험. TOFU는 OpenSSH 클라이언트가 채택한 사실상의 표준 정책으로, 키링 같은 부가 인프라 없이도 "최소한 같은 호스트에 두 번째 연결하면 알아챌 수 있다"는 보장을 준다.
- 정책 결정과 저장 책임을 `KnownHostsStore`가 갖고, russh 통합은 `TofuHandler`에 얇게 두는 것: 정책 변경(예: prompt-based 결정 추가) 시 핸들러만 손대면 됨.
- mismatch 시 일반 connect 에러로 묻히지 않도록 `Arc<Mutex<Option<TofuOutcome>>>`를 핸들러와 connect 코드가 공유. connect 실패 후 outcome을 읽어 `HostKeyMismatch`로 변환. (handler 자체는 connect()에 move 되어 직접 접근 불가)
- 사용자가 진짜 "서버 키가 정상적으로 바뀐 상황" (예: 서버 재설치)을 처리할 통로가 필요해 `ssh_trust_known_host` 명령을 별도로 노출. UI에서 위험 경고와 함께 명시적 동의를 받은 뒤에 호출하도록 의도.

### 어떻게
1. **KnownHostsStore**
   - `Mutex<()>`로 디스크 IO 직렬화 (멀티 세션 동시 connect 대비 race 방지).
   - `check(host, port, algorithm, fingerprint) -> MatchResult { FirstContact | Match | Mismatch { stored } }`.
   - `record`는 항상 덮어쓰기 — `check`에서 FirstContact일 때만 호출하면 첫 접속 등록, `ssh_trust_known_host`에서 호출하면 강제 갱신.
   - `forget`은 이미 없으면 `NotFound`.
2. **TofuHandler** (`session.rs`)
   - 핸들러는 `Arc<TofuShared>`를 들고, 외부에서도 `Arc::clone`으로 outcome을 관찰.
   - `check_server_key`: `server_public_key.algorithm().as_str()` + `.fingerprint(HashAlg::Sha256).to_string()`로 식별자 만들어 store에 조회.
3. **에러 변환** (`map_outcome_to_error`)
   - Mismatch → `HostKeyMismatch`
   - InternalError(IO/encoding) → `Connect("known_hosts: ...")`
   - Accepted/FirstContactRecorded → `None` (변환 안 함)
4. **Tauri 통합**
   - `SshState`에 `known_hosts: Arc<KnownHostsStore>` 추가.
   - `lib.rs setup`에서 `config_dir/wowterminal/{hosts,known_hosts}.toml` 경로 계산 후 `build_state`에 전달.
   - 3개 신규 커맨드 `invoke_handler`에 등록.
5. **테스트 트릭**
   - russh의 `PublicKey`를 테스트에서 생성하려면 ssh-key 0.7-rc의 rand_core 0.9 호환 RNG가 필요한데 우리 deps와 안 맞음. → 호스트에서 `ssh-keygen -t ed25519`로 미리 만든 두 개의 `ssh-ed25519` 공개키를 const로 박고 `PublicKey::from_openssh`로 파싱하는 방식 채택. 결정적이고 외부 RNG 의존 없음.
6. **검증**
   - `cargo check` ✅ (warning 0)
   - `cargo test --lib` ✅ **39 passed** (PTY 4 + AI 9 + Secrets 6 + SSH store 5 + SSH session 5 + known_hosts 6 + TofuHandler 4)
     - known_hosts: first_contact_then_match / mismatch / 다른 algorithm / port 분리 / forget 멱등 / record 덮어쓰기
     - TofuHandler: 첫 접속 저장+수락 / 같은 키 재접속 수락 / 다른 키 거절+Mismatch outcome / map_outcome_translates_mismatch
   - `npm run build` ✅

### 메모 / 한계
- IPv6 주소(예: `[fe80::1]:22`)는 단순한 `host:port` 키와 `rsplit_once(':')`에 잘 안 맞음. 현재는 zone 표기/괄호 없이 사용하는 호스트만 안전 — 후속에 별도 키 인코딩 도입 필요. TODO를 코드와 design 문서에 모두 명시.
- 첫 접속 시 "이 호스트는 처음입니다, fingerprint를 확인하세요" 같은 안내 UI는 미구현. v1에서는 silent record. 피싱/사칭 방지를 위해 v1.0 전 UI 노출 권장.
- `added_at`은 단순 epoch 문자열(`@unix:1716352800`). chrono 의존성 추가 없이 두기 위함. 사용자 표시용으로는 프론트엔드에서 변환.

### 다음 단계 후보

- HostKeyMismatch 에러를 UI에서 받았을 때 보여줄 경고 모달 + "신뢰하고 갱신" 버튼 → `ssh_trust_known_host` 호출
- 시크릿 unlock UX (앱 시작 시 마스터 패스프레이즈 입력)

## #7 — UI: HostKeyMismatch 경고 모달 + 신뢰하고 재시도

이슈: https://github.com/cuter74-dev/wowTerminal/issues/7

### 무엇을
- 백엔드
  - `SshError::HostKeyMismatch`에 `algorithm: String` 추가, `TofuOutcome::Mismatch`도 동반.
  - `ssh_connect` 반환 에러 타입을 `String`에서 구조화 enum `SshConnectError`로 변경 (`#[serde(tag = "kind")]`).
- 프론트엔드
  - `src/types.ts`에 `SshConnectError` 합집합 타입 + `isSshConnectError` 가드.
  - `<HostKeyMismatchModal>` — 빨강 테두리 경고 모달, host:port + algorithm + stored vs presented fingerprint 표시 (다른 색으로 구분), "취소" / "저장된 키 잊기" / "신뢰하고 재시도" 버튼.
  - `<Terminal>`에 `onSshError`, `retryNonce` prop 추가. SSH spawn 에러를 구조화 그대로 위로 전달.
  - `<App>`이 mismatch 상태를 들고 모달을 띄움, 신뢰 클릭 시 `ssh_trust_known_host` 호출 후 `retryNonce` 증가 → `<Terminal>` 재마운트 → 다시 connect.

### 왜
- 호스트 키 불일치는 **단순 connect 실패와 보안 사고를 구분해야 의미가 있는** 에러다. 기존 `Result<_, String>`이면 프론트가 메시지 substring 매칭으로 식별할 수밖에 없는데 그건 깨지기 쉽다. 구조화 enum + tag로 패턴 매칭이 가능하게 한다.
- `algorithm`을 에러에 포함한 이유: 사용자가 "신뢰하고 재시도"를 누르면 `ssh_trust_known_host(host, port, algorithm, fingerprint)`를 호출해야 하는데, 그러려면 algorithm을 알고 있어야 함. 모달이 이 정보를 직접 가지고 있는 게 깔끔.
- "저장된 키 잊기"를 별도 버튼으로 둔 이유: 사용자가 "정말 새 키인지 확신 못 함" 상황에서 일단 저장된 키를 지우고 다음 접속에서 first-contact로 새로 확인하고 싶을 수 있음. trust보다 한 단계 덜 위험한 행동.
- 모달은 빨강 테두리 + ⚠️ + 슬랙/전화 같은 별도 채널 확인 권고 문구로 **위험을 명시적으로 인지시킴**. UX보다 보안 우선.

### 어떻게
1. **백엔드 에러 변환**
   ```rust
   #[derive(Serialize)]
   #[serde(tag = "kind", rename_all = "snake_case")]
   pub enum SshConnectError {
       HostKeyMismatch { host, port, algorithm, stored, presented },
       Other { message: String },
   }
   impl From<SshError> for SshConnectError { ... }
   ```
   `ssh_connect`만 이 타입을 쓰고 나머지 명령은 그대로 String 에러 — 구조화가 필요한 곳만 비용을 치름.
2. **재마운트 트리거**
   - `<Terminal>`의 effect deps에 `retryNonce` 포함. 부모가 nonce를 증가시키면 cleanup → 재마운트 → 새 spawn.
   - 처음에 source가 같아서 sourceKey가 같더라도 nonce가 다르면 effect 재실행.
3. **프론트 에러 가드**
   ```ts
   export function isSshConnectError(e: unknown): e is SshConnectError {
     return typeof e === "object" && e !== null &&
       ((e as any).kind === "host_key_mismatch" || (e as any).kind === "other");
   }
   ```
4. **검증**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **39 passed** (algorithm 필드 추가에 따른 기존 테스트 보정 포함)
   - `npm run build` ✅ — 번들 538KB (gzip 149KB), 약간 증가는 모달 + 가드 코드.
   - GUI 실제 동작은 `npm run tauri dev` + 가짜 SSH 서버로 mismatch를 유도해 수동 검증 필요. 시나리오:
     1) 호스트 A 추가 → 첫 접속 → known_hosts 기록.
     2) 서버 측 호스트 키를 다른 ed25519 키로 교체.
     3) 다시 접속 → 빨간 모달 표시, stored/presented 다름 → "신뢰하고 재시도" → 새 키로 갱신 + 재접속 성공.

### 메모
- 첫 접속 안내(피싱 방지용) UI는 여전히 미구현 — 별도 이슈로 이어짐. 첫 접속에서도 fingerprint를 사용자에게 보여주고 "확인"을 누르게 하면 TOFU가 더 안전.
- `Other` 에러도 텍스트로 모달 띄울 여지 있음 (현재는 터미널 안에 한 줄로 표시). 구분 안 해도 사용성 큰 차이 없어 보여 일단 그대로.
- 모달이 떠 있는 동안 사용자가 사이드바에서 다른 호스트를 선택하면 모달 상태를 초기화하도록 `onSelect`에서 `setMismatch(null)` 호출.

## #8 — 보안: 첫 접속 확인 모달 (TOFU 강화)

이슈: https://github.com/cuter74-dev/wowTerminal/issues/8

### 무엇을
- 백엔드 정책 변경: 첫 접속 시 자동 저장 → 사용자 확인 요구.
  - `TofuOutcome::FirstContactRecorded` → `FirstContactPending { algorithm, fingerprint }`
  - `TofuHandler::check_server_key`가 first contact에 대해 `false` 반환 + outcome만 기록 (record 호출 X)
  - `SshError::FirstContactRequired { host, port, algorithm, fingerprint }` 신규
  - `SshConnectError::FirstContact { ... }` 신규
- 프론트엔드
  - `<FirstContactModal>` — 노랑/주황 톤 (경고는 맞지만 위험은 아님), fingerprint + algorithm 표시 + 서버에서 fingerprint 확인하는 ssh-keygen 명령 안내
  - `<App>`이 mismatch 모달과 first-contact 모달을 별도로 분기 관리
  - `<Terminal>`이 first-contact 에러도 노랑 메시지로 표시 + onSshError 전달
- 디자인 문서(`docs/design/ssh-manager.md`)의 TOFU 정책 섹션 업데이트, "첫 접속 안내 UI 미구현" 한계 제거
- 기존 테스트 갱신 + 신규 테스트 추가, 전체 **40 passed**

### 왜
- 기존 silent first-contact는 "처음 보는 호스트면 그게 누구든 일단 받아주고 같은 키로 다음에 와야 안다" — 첫 접속 시 누군가 MITM이면 그 사칭 키가 영구 기록됨. 진짜 TOFU의 의미를 살리려면 첫 fingerprint를 사용자에게 직접 보여주고 "맞다"를 받아야 함.
- 일관된 UX: HostKeyMismatch에서 이미 "신뢰하고 재시도" 흐름을 만들어 뒀으니 first-contact도 동일한 retry/trust 흐름(`ssh_trust_known_host` + `retryNonce` 증가)으로 재사용. 코드 변경 최소.
- 두 모달의 톤을 다르게 한 이유: first-contact는 정상 경로(노랑/🔐, 정보 안내 톤), mismatch는 비정상/위험(빨강/⚠️, 별도 채널 확인 강요). 색·아이콘으로 사용자가 위험도를 즉시 구분.
- ssh-keygen 안내 명령을 모달에 박은 이유: 사용자가 fingerprint를 어떻게 확인해야 할지 막막한 경우가 많음. "서버에서 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 실행" 같은 구체적 가이드가 결정적.

### 어떻게
1. **백엔드**
   ```rust
   Ok(MatchResult::FirstContact) => (
       false,
       TofuOutcome::FirstContactPending {
           algorithm: algorithm.clone(),
           fingerprint: fingerprint.clone(),
       },
   ),
   ```
   - `record` 호출 자체를 제거. trust는 오직 사용자 명시 동의로만 발생.
   - `map_outcome_to_error`가 FirstContactPending → `SshError::FirstContactRequired`로 변환.
2. **에러 enum 확장**
   - `SshConnectError`에 `FirstContact` variant 추가. `From<SshError>`에서 새 변환 추가.
3. **프론트 타입**
   - `SshConnectError` 합집합에 `{ kind: "first_contact", host, port, algorithm, fingerprint }` 추가.
   - `isSshConnectError` 가드도 `first_contact` 인식.
4. **App 상태 관리**
   - `mismatch`, `firstContact` 두 상태를 별도로 관리.
   - 두 모달 모두 `onTrusted`에서 동일하게 `retryNonce`를 증가시켜 `<Terminal>`이 재마운트되며 connect 재시도.
   - 사이드바에서 다른 호스트 선택 시 두 모달 모두 초기화 (`clearModalsAndSelect`).
5. **검증**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **40 passed** (기존 `first_contact_records_and_accepts` 폐기, 신규 `first_contact_requires_confirmation` / `user_trust_after_first_contact_then_match` / `map_outcome_translates_first_contact`)
   - `npm run build` ✅ — 541KB / gzip 149KB

### GUI 수동 검증 시나리오
1. 빈 known_hosts 상태에서 새 호스트 접속 시도 → 노랑 모달 + fingerprint 표시.
2. 서버에서 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 실행해 같은 fingerprint인지 확인.
3. "신뢰하고 접속" → 자동 재접속 성공.
4. 서버 호스트 키를 다른 키로 교체.
5. 다시 접속 → 빨강 mismatch 모달.
6. "신뢰하고 재시도" → 새 키 갱신 + 재접속 성공.

### 메모 / 한계
- 모달 안내의 `ssh_host_<algo>_key.pub` 경로 추정은 단순 문자열 치환 (`ssh-ed25519` → `ed25519`). 비표준 algorithm 이름이면 어색해질 수 있음 — 일반적 경우는 ed25519/rsa/ecdsa라 큰 문제 없음.
