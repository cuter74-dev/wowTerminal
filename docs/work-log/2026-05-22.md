## #3 — Secret store: keyring + Argon2id/AES-256-GCM file fallback

Issue: https://github.com/cuter74-dev/wowTerminal/issues/3

### What
- `SecretStore` trait + two implementations:
  - `KeyringStore`: OS keyring (libsecret / Keychain / Credential Manager)
  - `EncryptedFileStore`: a TOML file encrypted with AES-256-GCM by a user passphrase
- Plaintext secrets are always handled as `Zeroizing<Vec<u8>>` for auto-zeroize on drop.
- Added 6 unit tests (all passing).

### Why
- Must satisfy the CLAUDE.md security rule of **never storing secrets like API keys/SSH passphrases/passwords in plaintext in `backends.toml`/`hosts.toml`**.
- Why OS keyring first: most robust, and the user needn't memorize a separate passphrase.
- Why a passphrase file second: must also work on headless Linux / SSH-only environments / keyring-disabled environments.
- Why bind `id` into the AAD: blocks the scenario where an attacker edits the disk file to swap ciphertexts of different secrets (AEAD fails on AAD mismatch).

### How
1. **Dependencies** (`Cargo.toml`)
   - `keyring = "3"` (Linux: sync-secret-service, macOS: apple-native, Windows: windows-native)
   - `aes-gcm = "0.10"`, `argon2 = "0.5"`, `rand = "0.8"`, `zeroize`, `base64`, `toml`
2. **Module structure**
   ```
   src-tauri/src/secrets/
   ├── mod.rs              # SecretStore trait + SecretError + Secret(Zeroizing)
   ├── keyring_store.rs    # KeyringStore
   └── encrypted_file.rs   # EncryptedFileStore (TOML on-disk format)
   ```
3. **Disk format (`EncryptedFileStore`)**
   - `version`, `salt` (one Argon2id salt for the whole file), `[entries.<id>]` table with `nonce` + `ciphertext` (both base64).
   - Key derivation: `Argon2id(passphrase, salt, params=m:64MiB/t:3/p:1, 32B output)`.
   - Per secret: `nonce = OsRng.fill(12B)`; `ct = AES-256-GCM(kek, nonce, plaintext, aad=id)`.
4. **Error mapping**
   - AEAD failure (wrong passphrase / disk tampering) all map to the single `SecretError::BadPassphrase` — so the outside can't distinguish the two cases.
5. **Verification**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **15 passed** (9 existing + 6 new)
     - roundtrip / overwrite / delete (deleting a missing key is OK too)
     - reopen with a wrong passphrase → `BadPassphrase`
     - 1-byte ciphertext tamper → `BadPassphrase`
     - putting id A's ciphertext in id B's slot → `BadPassphrase` on AAD mismatch

### Notes
- `KeyringStore` is unusable in a headless environment without a Secret Service. A `CompositeStore` that tries the keyring in the integration code → falls back to `EncryptedFileStore` on failure will be introduced in the next step (with the ability to force a choice in user settings).
- The `keyring` crate accepts strings only, so arbitrary bytes are stored base64-encoded (restored on load).
- We unified AEAD-failure errors to `BadPassphrase`, but it can actually be either "wrong key" or "tampered data". For the user the action is the same in both (re-enter the passphrase), so it's fine.

### Next steps (issues #4~)
- Local shell via PTY + xterm.js
- russh-based SSH manager

## #4 — Local PTY + xterm.js terminal

Issue: https://github.com/cuter74-dev/wowTerminal/issues/4

### What
- Rust: `portable-pty`-based `PtyManager` (spawn/write/resize/kill) + reader thread → callback sink
- Tauri commands: `pty_spawn`, `pty_write`, `pty_resize`, `pty_kill`
- Tauri event: `pty:output { session_id, data_b64 }`
- Frontend: a `<Terminal>` component using `@xterm/xterm`, `@xterm/addon-fit`
- Replaced `App.tsx` with a single full-screen terminal
- Added 4 PTY unit tests (all passing, 19 total)

### Why
- A terminal app is essentially "PTY ↔ terminal renderer". Once this skeleton works, the next step can attach an SSH channel or a container via the same stream interface.
- Why make the data-passing abstraction a `DataSink` (`Arc<dyn Fn(SessionId, Vec<u8>)>`) callback: spawn → write → output verification must work even in a test environment without Tauri event emission. In the real app, `build_manager(&app)` wires the sink to `app.emit("pty:output", ...)`.
- Why wrap bytes in base64: PTY output is arbitrary bytes (8-bit, possibly non-UTF8), but Tauri's `serde_json` channel needs valid UTF-8. base64 is JSON-safe and light enough at ~33% overhead.

### How
1. **Rust dependency** (`portable-pty = "0.9"`)
2. **Module structure**
   ```
   src-tauri/src/pty/
   ├── mod.rs              # public API (PtyManager, SessionId, PtyError)
   ├── manager.rs          # core manager + DataSink abstraction, unit tests
   └── commands.rs         # Tauri command + event-emit sink creation
   ```
3. **`PtyManager` behavior**
   - `spawn(program, dims)`: `native_pty_system().openpty(...)` → `slave.spawn_command(...)` → split master writer/reader. The reader does a read loop on a separate OS thread → `(sink)(session_id, bytes)`.
   - `write` / `resize` / `kill`: look up in `Mutex<HashMap<SessionId, Session>>` then delegate. A missing id → `PtyError::NotFound`.
4. **Tauri integration** (`lib.rs`)
   - Create the manager via `build_manager(&app.handle())` in the `.setup` closure (the sink is an `app.emit("pty:output", payload)` closure).
   - Register `app.manage(PtyState(manager))`. Add the `pty_*` commands to the invoke_handler.
5. **Frontend** (`src/components/Terminal.tsx`)
   - Attach to the container via `@xterm/xterm` + `addon-fit`, track size with `ResizeObserver`.
   - `term.onData(s)` → `pty_write({sessionId, dataB64: base64(utf8(s))})`.
   - `listen("pty:output", ...)` → `term.write(base64decode(payload.data_b64))`.
   - dispose + call `pty_kill` in the `useEffect` cleanup.
6. **Verification**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **19 passed** (15 existing + 4 new)
     - send `echo wowterm-hello\nexit\n` to `/bin/sh` and confirm the marker received at the sink (stable since it includes both line echo + shell echo)
     - resize/write to a missing session → NotFound
     - session_count == 0 after kill
   - `npm run build` ✅ — TypeScript + Vite production build, 0 errors

### Notes / Limitations
- The real GUI (`npm run tauri dev`) needs a display server, so it can't be auto-verified in a headless environment. Wrapped up with non-GUI verification (cargo test + npm build); the user verifies on-screen key input/output separately.
- The `xterm` package is deprecated → replaced with `@xterm/xterm`.
- Since the data sink is callback-based, expensive sync emit (on every read) can be a burden. There's room to optimize later with mpsc + batch emit from a spawned tokio task. For now, simplest behavior first.

### Next steps (issue #5)
- russh-based SSH manager (host storage + UI)

## #5 — SSH manager: russh + hosts.toml + host UI

Issue: https://github.com/cuter74-dev/wowTerminal/issues/5

### What
- Rust module `src-tauri/src/ssh/`
  - `store.rs` — `HostStore`: `hosts.toml` CRUD
  - `session.rs` — `SshSession`: russh 0.61 client, PTY channel, actor pattern
  - `manager.rs` — `SshManager`: active-session HashMap
  - `commands.rs` — `ssh_list_hosts` / `ssh_save_host` / `ssh_delete_host` / `ssh_connect` / `ssh_write` / `ssh_resize` / `ssh_kill`
  - Event: `ssh:output` (same format as PTY, base64 payload)
- Frontend
  - `src/types.ts` — `SshHost`/`SshAuthMethod`/`TerminalSource` types
  - `<HostList>` — sidebar: Local shell + SSH host list, edit/delete icons, "+ New host"
  - `<HostForm>` — modal: name/host/port/user + auth (agent/password/private_key)
  - The `<Terminal>` component takes a `source` prop and branches local PTY/SSH
- Added 10 unit tests (host store 5, session helper 5).

### Why
- To complete the user scenario "SSH-connect with one host click", we need host storage + auth + channel + UI all together. Bundled into one issue.
- Why separate host metadata (`hosts.toml`) from secrets: metadata should be exportable/shareable by the user, but secrets must never be bundled. Decoupled via `*_secret_id` references.
- Why build the SSH session as an actor task + `mpsc` command channel: russh 0.61's `Channel` receives messages via `wait()`, so one thread/task must own it. To call `data()` / `window_change()` / `close()` from outside, you either send the channel itself or send commands. The latter is cleaner.
- Host-key verification unconditionally accepts in v1 (`PermissiveHandler`). For security, known_hosts TOFU must be introduced later — marked as a TODO in the code.

### How
1. **Dependencies** (`Cargo.toml`)
   - `russh = "0.61"`, `dirs = "5"`, `tempfile = "3"` (for tests)
2. **Session actor pattern**
   ```rust
   enum SessionCmd { Write(Vec<u8>), Resize { cols, rows }, Close }
   ```
   In a `tokio::spawn`ed task, receive cmds / handle channel messages via `tokio::select!`. Map to `data()` / `window_change()` / `eof()`+`close()`. External `SshSession::write/resize/close` only does an mpsc send.
3. **Auth flow** (`ResolvedAuth::from_method`)
   - `Password` → `SecretStore::load(secret_id)` → UTF-8 validation → russh `authenticate_password`
   - `PrivateKey` → key PEM + (optional) passphrase → `PrivateKey::from_openssh` (+ decrypt) → russh `authenticate_publickey`
   - `Agent` → unimplemented in v1. Explicit error.
   - `Debug` manually implemented as `<redacted>` to prevent secret exposure.
4. **Tauri State structure**
   - `SshState { manager, store, secrets: Option<Arc<dyn SecretStore>> }`
   - secrets has an incomplete unlock flow in v1 — left as None in state, and the `secrets_unlock` command returns "not implemented yet".
5. **Frontend integration**
   - Generalized via `<Terminal source={...}>`. A `commandsFor` helper dispatches `pty_*` + `pty:output` if local, `ssh_*` + `ssh:output` if ssh.
   - Source change in `<HostList>` → the Terminal component detects the `sourceKey` change and cleans up + starts a new session.
6. **Verification**
   - `cargo check` ✅ (0 warnings)
   - `cargo test --lib` ✅ — **29 passed** (PTY 4 + AI 9 + Secrets 6 + SSH store 5 + SSH session 5)
     - SSH store: empty/upsert+list/upsert update/delete not idempotent/serde roundtrip of 3 auth methods
     - SSH session: connect to a closed port → Connect or Auth error (fails within 5s timeout), ResolvedAuth password missing→Auth/utf8 decode/Agent NotImplemented/bad PEM parse failure
   - `npm run build` ✅ — TS+Vite no errors
   - **Manual GUI verification is a follow-up** — needs an environment with a display to add a host via `npm run tauri dev` → confirm up to connection attempt.

### Notes / Limitations
- The russh 0.61 API changed significantly vs 0.45 (Channel-centric, async fn in trait, `keys::PrivateKey`, etc.). Signatures differ a lot from older guides, so mind migration.
- The child keyring unlock + password/key registration UI flow is a follow-up issue. The current UI is at the stage of entering "a secret_id already registered in the secret store" as text.

## #6 — Security: introduce known_hosts TOFU

Issue: https://github.com/cuter74-dev/wowTerminal/issues/6

### What
- `KnownHostsStore` (`src-tauri/src/ssh/known_hosts.rs`) — `host:port → {algorithm, fingerprint, added_at}` mapping, TOML file (`~/.config/wowterminal/known_hosts.toml`)
- `TofuHandler` replaces `PermissiveHandler`. In `russh::Handler::check_server_key`:
  - First contact: store + accept
  - Match: accept
  - Mismatch: reject + record `TofuOutcome::Mismatch`
- Added `SshError::HostKeyMismatch { host, port, stored, presented }`. When session connect fails, check the outcome and convert to this clear error instead of a generic Connect error.
- Added 3 Tauri commands: `ssh_list_known_hosts`, `ssh_forget_known_host`, `ssh_trust_known_host(host, port, algorithm, fingerprint)`
- Updated `SshState`/`build_state`/`lib.rs setup` to take the `known_hosts.toml` path and share the store with the manager.
- Documented policy/format/limitations in `docs/design/ssh-manager.md`.
- Added 10 unit tests (KnownHostsStore 6 + TofuHandler 4). **39 passed** total.

### Why
- The existing `PermissiveHandler` accepts any server key → risk of the user sending credentials to a spoofed server on MITM. TOFU is the de facto standard policy adopted by the OpenSSH client and gives the guarantee "at least on the second connection to the same host, you'll notice" without extra infrastructure like a keyring.
- `KnownHostsStore` owns the policy decision and storage responsibility, with the russh integration kept thin in `TofuHandler`: on a policy change (e.g. adding prompt-based decisions) only the handler needs touching.
- So a mismatch isn't buried as a generic connect error, the handler and connect code share an `Arc<Mutex<Option<TofuOutcome>>>`. After a connect failure, read the outcome and convert to `HostKeyMismatch`. (The handler itself is moved into connect() so it can't be accessed directly)
- The user needs a path to handle a genuine "the server key legitimately changed" situation (e.g. server reinstall), so the `ssh_trust_known_host` command is exposed separately. Intended to be called from the UI only after explicit consent with a danger warning.

### How
1. **KnownHostsStore**
   - Serialize disk IO with `Mutex<()>` (prevents races on concurrent multi-session connect).
   - `check(host, port, algorithm, fingerprint) -> MatchResult { FirstContact | Match | Mismatch { stored } }`.
   - `record` always overwrites — calling it only on FirstContact registers the first contact; calling it from `ssh_trust_known_host` force-updates.
   - `forget` returns `NotFound` if already missing.
2. **TofuHandler** (`session.rs`)
   - The handler holds `Arc<TofuShared>`, and the outside can also observe the outcome via `Arc::clone`.
   - `check_server_key`: build the identifier from `server_public_key.algorithm().as_str()` + `.fingerprint(HashAlg::Sha256).to_string()` and look it up in the store.
3. **Error conversion** (`map_outcome_to_error`)
   - Mismatch → `HostKeyMismatch`
   - InternalError(IO/encoding) → `Connect("known_hosts: ...")`
   - Accepted/FirstContactRecorded → `None` (no conversion)
4. **Tauri integration**
   - Added `known_hosts: Arc<KnownHostsStore>` to `SshState`.
   - In `lib.rs setup`, compute the `config_dir/wowterminal/{hosts,known_hosts}.toml` paths then pass to `build_state`.
   - Registered the 3 new commands in the `invoke_handler`.
5. **Test trick**
   - Creating a russh `PublicKey` in tests needs a rand_core 0.9-compatible RNG for ssh-key 0.7-rc, which doesn't match our deps. → Adopted the approach of hardcoding two `ssh-ed25519` public keys (pre-made on the host via `ssh-keygen -t ed25519`) as consts and parsing them with `PublicKey::from_openssh`. Deterministic and no external RNG dependency.
6. **Verification**
   - `cargo check` ✅ (0 warnings)
   - `cargo test --lib` ✅ **39 passed** (PTY 4 + AI 9 + Secrets 6 + SSH store 5 + SSH session 5 + known_hosts 6 + TofuHandler 4)
     - known_hosts: first_contact_then_match / mismatch / different algorithm / port separation / forget idempotent / record overwrite
     - TofuHandler: first contact store+accept / same-key reconnect accept / different-key reject+Mismatch outcome / map_outcome_translates_mismatch
   - `npm run build` ✅

### Notes / Limitations
- IPv6 addresses (e.g. `[fe80::1]:22`) don't fit the simple `host:port` key and `rsplit_once(':')` well. Currently only hosts used without zone notation/brackets are safe — a follow-up needs separate key encoding. TODO noted in both code and the design doc.
- Guidance UI on first contact like "this host is new, verify the fingerprint" isn't implemented. v1 silently records. Recommend exposing the UI before v1.0 to prevent phishing/spoofing.
- `added_at` is a simple epoch string (`@unix:1716352800`). To avoid adding a chrono dependency. Convert in the frontend for user display.

### Next-step candidates
- First-contact guidance UI (a chance for the user to verify the fingerprint)
- A warning modal to show on receiving a HostKeyMismatch error in the UI + a "trust and update" button → call `ssh_trust_known_host`
- Secret unlock UX (master-passphrase input at app start)
- ssh-agent delegated auth

## #7 — UI: HostKeyMismatch warning modal + trust and retry

Issue: https://github.com/cuter74-dev/wowTerminal/issues/7

### What
- Backend
  - Added `algorithm: String` to `SshError::HostKeyMismatch`, accompanied by `TofuOutcome::Mismatch`.
  - Changed the `ssh_connect` return error type from `String` to the structured enum `SshConnectError` (`#[serde(tag = "kind")]`).
- Frontend
  - `SshConnectError` union type + `isSshConnectError` guard in `src/types.ts`.
  - `<HostKeyMismatchModal>` — red-bordered warning modal, shows host:port + algorithm + stored vs presented fingerprint (color-distinguished), "Cancel" / "Forget the stored key" / "Trust and retry" buttons.
  - Added `onSshError`, `retryNonce` props to `<Terminal>`. Passes the SSH spawn error up, structured as-is.
  - `<App>` holds the mismatch state and shows the modal; on trust click it calls `ssh_trust_known_host` then increments `retryNonce` → `<Terminal>` remount → reconnect.

### Why
- A host-key mismatch is an error that only matters if you **distinguish a plain connect failure from a security incident**. With the old `Result<_, String>`, the frontend would have to identify it by message substring matching, which is fragile. A structured enum + tag enables pattern matching.
- Why include `algorithm` in the error: when the user clicks "Trust and retry", we must call `ssh_trust_known_host(host, port, algorithm, fingerprint)`, which requires knowing the algorithm. It's cleanest for the modal to hold this info directly.
- Why a separate "Forget the stored key" button: when the user "isn't sure it's really a new key", they may want to delete the stored key first and re-verify via first-contact on the next connection. One step less dangerous than trust.
- The modal **explicitly makes the danger felt** with a red border + ⚠️ + advice to verify via a separate channel like Slack/phone. Security over UX.

### How
1. **Backend error conversion**
   ```rust
   #[derive(Serialize)]
   #[serde(tag = "kind", rename_all = "snake_case")]
   pub enum SshConnectError {
       HostKeyMismatch { host, port, algorithm, stored, presented },
       Other { message: String },
   }
   impl From<SshError> for SshConnectError { ... }
   ```
   Only `ssh_connect` uses this type; the rest keep String errors — paying the cost only where structure is needed.
2. **Remount trigger**
   - Include `retryNonce` in the `<Terminal>` effect deps. When the parent increments the nonce → cleanup → remount → new spawn.
   - Even if the source is the same so sourceKey is the same, a different nonce re-runs the effect.
3. **Frontend error guard**
   ```ts
   export function isSshConnectError(e: unknown): e is SshConnectError {
     return typeof e === "object" && e !== null &&
       ((e as any).kind === "host_key_mismatch" || (e as any).kind === "other");
   }
   ```
4. **Verification**
   - `cargo check` ✅
   - `cargo test --lib` ✅ — **39 passed** (including fixing existing tests for the added algorithm field)
   - `npm run build` ✅ — bundle 538KB (gzip 149KB), the slight increase is the modal + guard code.
   - Real GUI behavior needs manual verification by inducing a mismatch with `npm run tauri dev` + a fake SSH server. Scenario:
     1) Add host A → first connect → known_hosts recorded.
     2) Replace the server-side host key with a different ed25519 key.
     3) Reconnect → red modal shown, stored/presented differ → "Trust and retry" → update to the new key + reconnect succeeds.

### Notes
- The first-contact guidance (anti-phishing) UI is still unimplemented — continued as a separate issue. Showing the fingerprint to the user even on first contact and having them click "confirm" makes TOFU safer.
- An `Other` error could also be shown as a modal (currently shown as one line inside the terminal). Not distinguishing it doesn't change usability much, so left as-is for now.
- If the user selects another host in the sidebar while the modal is up, `onSelect` calls `setMismatch(null)` to reset the modal state.

- First-contact guidance modal (user fingerprint confirmation)
- Secret unlock UX (master passphrase)

## #8 — Security: first-contact confirmation modal (TOFU hardening)

Issue: https://github.com/cuter74-dev/wowTerminal/issues/8

### What
- Backend policy change: auto-store on first contact → require user confirmation.
  - `TofuOutcome::FirstContactRecorded` → `FirstContactPending { algorithm, fingerprint }`
  - `TofuHandler::check_server_key` returns `false` for first contact + records the outcome only (no record call)
  - New `SshError::FirstContactRequired { host, port, algorithm, fingerprint }`
  - New `SshConnectError::FirstContact { ... }`
- Frontend
  - `<FirstContactModal>` — yellow/orange tone (a warning, but not a danger), shows fingerprint + algorithm + the ssh-keygen command to verify the fingerprint on the server
  - `<App>` manages the mismatch modal and the first-contact modal as separate branches
  - `<Terminal>` shows the first-contact error too as a yellow message + passes onSshError
- Updated the TOFU policy section in the design doc (`docs/design/ssh-manager.md`), removed the "first-contact guidance UI unimplemented" limitation
- Updated existing tests + added new tests, **40 passed** total

### Why
- The old silent first-contact means "if it's a host you've never seen, accept whoever it is, and you only find out when someone comes with the same key next time" — if someone MITMs on first contact, that spoofed key is permanently recorded. To realize true TOFU, you must show the first fingerprint to the user and get a "yes, correct".
- Consistent UX: since the "trust and retry" flow was already built for HostKeyMismatch, first-contact reuses the same retry/trust flow (`ssh_trust_known_host` + increment `retryNonce`). Minimal code change.
- Why differ the two modals' tones: first-contact is the normal path (yellow/🔐, informational tone), mismatch is abnormal/dangerous (red/⚠️, forcing separate-channel verification). Color·icon let the user instantly distinguish the risk level.
- Why embed the ssh-keygen guidance command in the modal: users often have no idea how to verify a fingerprint. A concrete guide like "run `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the server" is decisive.

### How
1. **Backend**
   ```rust
   Ok(MatchResult::FirstContact) => (
       false,
       TofuOutcome::FirstContactPending {
   ```

### GUI manual verification scenario
1. Attempt to connect a new host with an empty known_hosts state → yellow modal + fingerprint shown.
2. Run `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the server to confirm the same fingerprint.
3. "Trust and connect" → auto-reconnect succeeds.
4. Replace the server host key with a different key.
5. Reconnect → red mismatch modal.
6. "Trust and retry" → update to the new key + reconnect succeeds.

### Notes / Limitations
- The modal guidance's `ssh_host_<algo>_key.pub` path inference is a simple string substitution (`ssh-ed25519` → `ed25519`). A non-standard algorithm name could look awkward — but common cases are ed25519/rsa/ecdsa so no big issue.
- There's no way to re-trigger a reconnect to the same host while the modal is up (clicking the sidebar closes the modal and switches to a new source).
