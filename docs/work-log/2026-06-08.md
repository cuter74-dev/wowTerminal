## #83 — Newest-macOS input duplication (IME) + SSH-connect screen clear

GitHub #83 (English) / GitLab #2 (Korean).

### What / Why / How
- Reported by a downstream user; their machine is a **Mac, M5 (newest macOS)**. Not reproducible on the maintainer's machine or older macOS — so launching a dev build locally does NOT reproduce it. This was the key clue: it's a **newest-WKWebView behavior** issue.
- **Input duplication** (`df -h` → `dddff f -h`): the custom IME mirror in `Terminal.tsx` was built for OLD WKWebView that doesn't fire `compositionstart/end` (only keyCode 229). The newest macOS WKWebView fires proper composition events, and even English input goes through composition (inline predictive text). So xterm's native IME handling AND our mirror both wrote the input → duplication.
  - Fix: added `nativeComposition` flag set on the first `compositionstart`. When set, the keyCode-229 path returns `true` (let xterm's native IME handle it) instead of engaging the custom mirror. Old WKWebView (no composition events) keeps the mirror unchanged. Auto-adapting, low risk to the working path. **Needs the M5 user to confirm** (can't reproduce locally).
- **SSH connect screen wipe**: #81 auto-injected a remote OSC 7 cwd hook 0.5s after connect, ending with `\r\x0c` — the Ctrl-L cleared the whole screen including the banner/MOTD. Same fragile runtime-injection approach already abandoned for the local shell in #37.
  - Fix: removed `REMOTE_OSC7_SETUP` and the injection spawn in `session.rs`. The OSC 7 *receive* handler stays.
- **Remote cwd (non-invasive)**: rather than a fragile silent injection (hiding the echoed setup line is unreliable across prompts/wrap/tmux — proven by #34/#37), the robust non-invasive path is iTerm-style: the user adds one line to their remote shell rc and we track via OSC 7 receive. Snippet documented in `docs/guide/ssh.md`. Until added, SSH drag-upload falls back to the remote home.

### Verification
- `cargo check` ✅ / `npm run build` ✅. (Behavior on the newest macOS pending the M5 user's test — the only reproduction.)

### Follow-up — non-invasive remote cwd (method C, implemented & confirmed working)
- After removing the injection, drag-upload and the file browser fell back to the remote home. Rather than re-injecting (artifact) or requiring an rc-hook per host, implemented an on-demand `/proc`-based lookup.
- Mechanism (validated empirically against a real Linux host over multiplexed SSH): in one SSH connection the interactive shell and any exec channel are descendants of the same per-connection sshd. At drag/open time we open a separate exec channel and run a POSIX-sh script that walks its own ancestry to find the connection sshd, then finds the descendant that has a controlling tty (= the interactive shell) and reads `/proc/<pid>/cwd`. Our exec has no tty so it's excluded; the connection-sshd disambiguation (vs the shared listener sshd) ensures we don't match another connection's shell.
- `session.rs`: keep the russh `Handle` in an `Arc` (it isn't `Clone`); `remote_cwd()` opens the exec channel and runs the script under a 2s timeout. `manager.rs`/`commands.rs`/`lib.rs`: `ssh_remote_cwd(session_id) -> Option<String>`. `App.tsx`: drag handler and `onOpenFiles` use OSC 7 → `ssh_remote_cwd` → home in that priority.
- Linux remotes only; macOS/BSD/hidepid/containers return null → graceful home fallback (no breakage). `ssh.md` documents the optional OSC 7 rc-hook for non-Linux remotes.
- User-confirmed: drag-upload and the file browser both open at the remote current directory.
