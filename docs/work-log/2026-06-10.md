## #83 ROOT CAUSE — M5 dup persists in v0.13.11; predictive text is the real culprit (v0.13.12)

GitHub #83 (English) / GitLab #2 (Korean).

### What / Why / How
- The M5 user's screenshot on v0.13.11 still showed `df -h` → `ddf -hdff f -h` at the prompt (command executed correctly). So the v0.13.6 WebGL renderer theory was wrong.
- Re-read the v0.13.5 `wt-ime-diag` traces in GlitchTip — the M5 (isMac) traces had been there all along:
  `nCS:0 nCU:0 nCE:0 | n229:3 | mirrorChars:15 mirrorBs:10 | onDataChars:0` for typing `df -h` (5 keys).
- What this proves:
  1. **M5 fires NO composition events** (`nCS=0`) — the #83 `nativeComposition` bypass never engaged there; the whole "newest WKWebView fires composition events" premise was wrong.
  2. English keystrokes hit **keyCode 229** (3 of them) → the custom IME mirror engaged.
  3. macOS **inline predictive text ("writing suggestions") rewrites the hidden textarea**, so the mirror's prefix-diff sent a backspace+resend storm — 15 chars + 10 backspaces for 5 keystrokes. Net = 5, so the shell line was correct and the command ran; but the churn interleaved with oh-my-zsh's per-keystroke line redraw leaves real stray characters in the xterm buffer. That's why WebGL (full repaint) didn't help — the junk is buffer content, not stale glyphs. And why other terminals are clean — they have no mirror.
- Fix (`Terminal.tsx`): right after `term.open()`, set `term.textarea.setAttribute("writingsuggestions", "false")` — the WebKit attribute that disables inline predictive text (xterm only sets autocorrect/autocapitalize/spellcheck, which don't cover it). With suggestions off, English no longer routes through keyCode 229, the mirror never engages for plain typing, and only real IME composition (Korean etc.) uses it. Also corrected the WebGL comment (kept for GPU accel, but it was not the #83 fix).
- `npm run build` ✅. Needs the M5 user to confirm (the maintainer's machine never reproduced — its trace is `n229:0, onDataChars:5`, pure plain path).
