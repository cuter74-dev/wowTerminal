# 2026-08-10

## #140 — 한글 조합을 커밋하는 스페이스가 중복/누락되던 문제

### What / Why
- 제보: "한글을 쓸 때 윈도우/맥에서 띄어쓰기 할 때 중복 또는 이상하게 반응할 때가 있어."
- GlitchTip 진단은 API 토큰이 없어 접근 불가 → **배송되는 xterm 6.0.0 소스 추적 + 자가 테스트 실측**으로 검증했다.

### 원인 (xterm 6.0.0 `CompositionHelper` + `CoreBrowserTerminal`)
- 조합을 커밋하는 스페이스 keydown이 `isComposing=true` + 실제 keyCode(32)로 들어오면(229가 아니라):
  1. `CompositionHelper.keydown` → `_finalizeComposition(false)` — 조합 중 음절 **즉시 전송**
  2. keydown 계속 진행 → 스페이스 전송
  3. `compositionend` → `_finalizeComposition(true)`의 setTimeout이 **textarea를 다시 읽어 음절 재전송**
- Enter 커밋이 안 겹치는 이유: xterm이 CR에서 `textarea.value=''`로 비운다. **스페이스는 비우기가 없다** → Windows류(가드 없음)에선 `가 가` 중복.
- macOS 조합 머신에선 #100 가드(조합 중 onData 폐기)가 1·2번 전송을 삼킨다(아직 `composing=true`) → 3번만 남아 **공백이 사라진다**.
- 스페이스 keydown이 229로 오는 IME/상황에선 정상 → "가끔"의 정체.

### 실측 (자가 테스트 T7 신설)
- `inputSelfTest.ts`에 T7 추가 — 실제 이벤트 순서 그대로 합성: CS → CU/insertCompositionText → **스페이스 keydown(keyCode 32, isComposing=true)** → CE. 커밋 텍스트는 실 브라우저처럼 textarea에 남겨 xterm의 지연 재읽기가 동작하게 한다.
- **수정 전**: `/tmp/wt-st7.txt` = `st7-가x` — 공백 소실(mac 증상 재현) ✓
- **수정 후**: `st7-가 x` — 정확히 "음절, 공백" 1회씩 ✓. T1~T6 회귀 없음.

### How (`src/components/Terminal.tsx`)
- 조합 중 스페이스 keydown(`(e.isComposing || composing) && !imeActive`, 모디파이어 없음)을 **preventDefault로 삼키고** `pendingComposedSpace` 플래그만 세운다 — xterm의 즉시 전송(1·2번)이 아예 발생하지 않는다.
- **전 플랫폼** `compositionend` 리스너(신설)가 플래그를 소비해 `setTimeout(0)`으로 공백을 보낸다. xterm의 compositionend 리스너가 **먼저 등록**돼 음절 전송 타임아웃을 먼저 큐잉하므로, 큐 순서상 항상 "음절 → 공백".
- 조합이 계속되는 IME(일본어 변환 스페이스 등)는 compositionend가 안 와 플래그가 남는데, 다음 keydown에서 폐기 — 변환 키가 리터럴 공백으로 새지 않는다.
- 미러 경로(229-only macOS)는 isComposing/composing이 항상 false라 미개입.

### 검증 환경 메모
- Synology Drive 폴더에서 vite/rsync가 죽은 placeholder 파일들로 반복 실패(ETIMEDOUT) → `git archive HEAD`로 `/private/tmp/wt140`에 로컬 사본을 만들어 dev 앱을 돌렸다. `node_modules`는 `npm ci`로 재설치(원본 폴더의 깨진 것은 `node_modules.broken`으로 치워둠 — 정리 필요).
- 셀프테스트 기동은 dev에서 `main.tsx`에 임시 플래그 세팅(+온보딩 생략)을 넣고 vite full reload로 트리거(커밋 전 제거).

### 남은 확인
