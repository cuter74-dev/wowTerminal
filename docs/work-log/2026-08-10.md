## #140 — 한글 조합을 커밋하는 스페이스가 중복/누락되던 문제

### What / Why
- 제보: "한글을 쓸 때 윈도우/맥에서 띄어쓰기 할 때 중복 또는 이상하게 반응할 때가 있어."
- GlitchTip 진단은 API 토큰이 없어 접근 불가 → **배송되는 xterm 6.0.0 소스 추적 + 자가 테스트 실측**으로 검증했다.

### 원인 (xterm 6.0.0 `CompositionHelper` + `CoreBrowserTerminal`)
- 조합을 커밋하는 스페이스 keydown이 `isComposing=true` + 실제 keyCode(32)로 들어오면(229가 아니라):
  1. `CompositionHelper.keydown` → `_finalizeComposition(false)` — 조합 중 음절 **즉시 전송**
  2. keydown 계속 진행 → 스페이스 전송
  3. `compositionend` → `_finalizeComposition(true)`의 setTimeout이 **textarea를 다시 읽어 음절 재전송**
- Enter 커밋이 안 겹치는 이유: xterm이 CR에서 `textarea.value=''`로 비운다. **스페이스는 비우기가 없다** → Windows류(가드 없음)에선 `가 가` 중복.
- macOS 조합 머신에선 #100 가드(조합 중 onData 폐기)가 1·2번 전송을 삼킨다(아직 `composing=true`) → 3번만 남아 **공백이 사라진다**.
- 스페이스 keydown이 229로 오는 IME/상황에선 정상 → "가끔"의 정체.

### 실측 (자가 테스트 T7 신설)
- `inputSelfTest.ts`에 T7 추가 — 실제 이벤트 순서 그대로 합성: CS → CU/insertCompositionText → **스페이스 keydown(keyCode 32, isComposing=true)** → CE. 커밋 텍스트는 실 브라우저처럼 textarea에 남겨 xterm의 지연 재읽기가 동작하게 한다.
- **수정 전**: `/tmp/wt-st7.txt` = `st7-가x` — 공백 소실(mac 증상 재현) ✓
- **수정 후**: `st7-가 x` — 정확히 "음절, 공백" 1회씩 ✓. T1~T6 회귀 없음.

### How (`src/components/Terminal.tsx`)
- 조합 중 스페이스 keydown(`(e.isComposing || composing) && !imeActive`, 모디파이어 없음)을 **preventDefault로 삼키고** `pendingComposedSpace` 플래그만 세운다 — xterm의 즉시 전송(1·2번)이 아예 발생하지 않는다.
- **전 플랫폼** `compositionend` 리스너(신설)가 플래그를 소비해 `setTimeout(0)`으로 공백을 보낸다. xterm의 compositionend 리스너가 **먼저 등록**돼 음절 전송 타임아웃을 먼저 큐잉하므로, 큐 순서상 항상 "음절 → 공백".
- 조합이 계속되는 IME(일본어 변환 스페이스 등)는 compositionend가 안 와 플래그가 남는데, 다음 keydown에서 폐기 — 변환 키가 리터럴 공백으로 새지 않는다.
- 미러 경로(229-only macOS)는 isComposing/composing이 항상 false라 미개입.

### 검증 환경 메모
- Synology Drive 폴더에서 vite/rsync가 죽은 placeholder 파일들로 반복 실패(ETIMEDOUT) → `git archive HEAD`로 `/private/tmp/wt140`에 로컬 사본을 만들어 dev 앱을 돌렸다. `node_modules`는 `npm ci`로 재설치(원본 폴더의 깨진 것은 `node_modules.broken`으로 치워둠 — 정리 필요).
- 셀프테스트 기동은 dev에서 `main.tsx`에 임시 플래그 세팅(+온보딩 생략)을 넣고 vite full reload로 트리거(커밋 전 제거).

### 남은 확인
- 합성 이벤트 기준 검증이므로, **실제 IME**(맥 한글 2벌식·Windows MS IME)로 띄어쓰기 확인 후 이슈를 닫는다.

## #141 — Windows 파일 탐색기 휠 스크롤 불능

### What / Why
- 제보: Windows에서 파일 탐색기 목록에 휠을 굴려도 안 움직임. 같은 머신에서 터미널 스크롤은 정상.
- 증상 분리로 원인 반경 확정: 터미널은 **xterm이 wheel을 JS로 처리**(네이티브 스크롤 미사용) → wheel 이벤트는 웹뷰에 정상 도달. 파일 탐색기는 CSS `overflow-y:auto` **네이티브 스크롤** 의존 → WebView2가 이 오버레이의 네이티브 휠 스크롤을 처리하지 않는 상황.
- 앱 코드에 wheel을 막는 곳 없음, flex 체인(`minHeight:0`)도 건전 — WebView2 쪽 정확한 트리거는 미상(Windows 재현 환경 없음). 원인 불명이어도 확실히 동작하는 쪽으로: **휠을 JS로 직접 처리**(탭바 #124에서 검증된 접근).

### How (`FileBrowser.tsx`)
- `useWheelScroll()` 훅 신설 — wheel을 `passive:false`로 직접 등록해 `scrollTop += deltaY`(deltaMode 라인=×16/페이지=×높이 환산) + `preventDefault`.
  - preventDefault로 네이티브 스크롤을 눌러 **정상 환경(macOS)에서 이중 스크롤이 없다.**
  - React `onWheel`은 root에 passive로 위임돼 preventDefault 불가 → ref + addEventListener.
  - `Ctrl+휠`(줌 제스처)은 통과.
- 적용 3곳: 파일 목록 패널(Panel, 로컬/원격) · 전송 큐(TransferQueue) · 원격 검색 결과(SearchModal).

### 남은 확인
- Windows 실기기에서 휠 동작 확인 후 이슈 클로즈. macOS 휠·트랙패드 회귀도 실기기 확인.

## #142 — Android: 호스트 추가가 "io error"로 실패

### What / Why
- 제보: Android 태블릿에서 호스트를 추가하면 io 에러가 나며 등록되지 않음.
- 에러 문자열이 `HostStoreError::Io`의 `"io error: {0}"`와 정확히 일치 — 저장 경로 문제로 특정.

### 원인
- `lib.rs`가 설정 디렉토리를 `dirs::config_dir()`로 잡는데, **dirs 크레이트는 Android를 데스크탑 Linux처럼 취급**해 `$XDG_CONFIG_HOME` → `$HOME/.config`을 반환한다. Android 앱 프로세스에는 둘 다 없다:
  - `HOME` 미설정 → `None` → 폴백 `"."` = 프로세스 CWD(`/`)
  - `HOME=/` → `/.config/wowterminal`
- 어느 쪽이든 쓰기 불가 → `create_dir_all` 실패가 `let _`로 무시된 채 `hosts.toml` 쓰기에서 io error. 같은 `config_dir`를 쓰는 **모든 저장소**(known_hosts/groups/tags/keys/backends.toml/secrets.enc)가 같이 죽어 있었다.
- iOS가 정상인 이유: 샌드박스 `$HOME`이 설정돼 있어 dirs가 유효한 앱 컨테이너 경로를 반환(App Store 출시본이 증거).

### How (`src-tauri/src/lib.rs`)
- `#[cfg(target_os = "android")]`에서만 Tauri `app.path().app_config_dir()` 사용 — Kotlin 플러그인의 `getConfigDir`(앱 내부 저장소, `/data/user/0/<pkg>/…`)를 반환한다(tauri-2.11.2 `path/android.rs` 소스로 확인).
- 데스크탑·iOS는 기존 `dirs` 경로 유지 — **기존 설치 사용자의 데이터 위치를 바꾸지 않는다.** Android는 여태 저장이 안 됐으니 잃을 데이터가 없다.

### 검증
- 데스크탑 `cargo check` 통과. Android 크로스 컴파일은 이 맥에 NDK가 없어 불가 — cfg 브랜치 문법은 데스크탑 빌드의 파싱이 보증하고, `app_config_dir` API 존재는 tauri 소스로 확인.
- **실기기 검증 필요**: Android 빌드를 올려 호스트 추가가 저장되는지 확인 후 이슈 클로즈.

## #143 — 백스페이스가 중간부터 안 먹던 버그 (로그 실측으로 원인 확정)

### 추적 방법
- GlitchTip 접근이 없어, 기존 진단 링(kd/input/echo/lines/ring)을 **로컬 파일로도 덤프하는 임시 코드**를 dev 사본에 넣고(`/tmp/wt-bs-diag.jsonl`), 사용자가 실제 증상을 재현 → 로그 삼분법(입력/셸/렌더러)으로 원인 확정. 임시 덤프는 커밋하지 않음.

### 원인 두 개 (macOS 미러 경로)
1. **미러 텍스트 고갈 시 백스페이스 증발** (주 원인): 붙여넣기(#97 정리로 textarea에서 제거됨) 후 한글을 치면 미러 기준선은 빈 값 + 한글만. 백스페이스로 한글이 다 지워져 textarea가 비면, 이후 백스페이스는 기본 동작에 맡겨지는데 **빈 textarea에는 input 이벤트가 없다** → `\x7f`가 PTY로 전혀 안 가 셸에 남은 붙여넣기 텍스트를 지울 수 없음. 실측 재현: "한글은 지워지는데 붙여넣기한 부분부터 백스페이스가 안 먹어."
   - 수정: 그 경우 `\x7f`를 직접 전송(미러 상태는 빈 그대로라 오염 없음).
2. **NBSP 플립로 인한 diff 오염**: #100은 전송 직전에만 NBSP를 정규화하고 `imeSent`에는 원본을 저장했다. macOS가 삭제 도중 스페이스를 NBSP로 되돌려 쓰면 U+0020≠U+00A0 불일치로 백스페이스 1타마다 `\x7f\x7f␣`(2 되감기+스페이스 재전송)가 나갔다 — 실측 ring: `s='…제대로 적' → f='…제대로\xa0'`. 좁은 분할 패널(cols=22)의 랩된 줄에서 원격 bash 재그리기와 얽혀 잔여를 만들었다.
   - 수정: flushMirror가 **비교 전에** 정규화 — 비교·저장·전송이 전부 정규화 값으로 통일, 플립은 no-op.

### 검증
- 사용자 실기기 재현 → 수정 후 "이제 삭제가 되고 있어" 확인. `tsc --noEmit` 통과.
- Windows/태블릿에서도 유사 증상 제보가 있었는데 진단 링이 macOS 한정 수집이라 미확인 — 재발하면 수집 게이트를 열어 같은 방법으로 추적.
